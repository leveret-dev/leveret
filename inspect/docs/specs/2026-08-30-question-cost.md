# Question Cost: A Ladder, Not a Ladder-Climb

**Date:** 2026-08-30
**Status:** Analysis. Amends nothing directly; recommends re-reading `docs/specs/2026-08-29-code-graph-sourcing.md` sections 5.1–5.3 against the mapping in section 3 below.
**Method:** internal document analysis only. No external fetch. Every row cites a repository file and section.

## 1. The hypothesis

**Claim to test:** the shipping products (CodeRabbit and peers) need no build because the questions they answer are cheaper than the ones we set out to answer — not because they solved a harder problem more cleverly. If true, our comparison against them (`docs/specs/2026-08-29-coderabbit-approach.md`) was mis-framed as "can we match their fidelity without a build", when the real question is "which of *our own* questions actually require a build".

**Verdict, stated first:** the hypothesis is correct, and our own documents already contain the evidence — `docs/specs/2026-08-29-code-graph-sourcing.md` §5 built exactly this ladder (the "basis" table) on 2026-08-29 without naming it a ladder or mapping it back to the five product goals. This document performs that mapping and finds three places where our own prose still assumes a higher rung than the goal in front of it needs.

## 2. The question-cost ladder

Five rungs, ordered by minimum input. Each row cites the spec section that supports the cost claim, not an external source — the constraint is analysis over material already in this repository.

| # | Question | Minimum input | Rung | Cites |
|---|---|---|---|---|
| 1 | Secret in a literal; Unicode-security bidi/tag/variation-selector abuse | one file's decoded content; no parse tree, no cross-file state | **file, no semantics** | `specs/analyzers/text-and-secrets/specification.md` §4.4 ("content-level binary handling" is line-by-line character scanning, not parsing), §6 (bidi/tag/variation rules are per-line code-point scans), §5.1 (stages: select file → read → dispatch regex/entropy checks — no AST) |
| 2 | IaC misconfiguration (e.g. `S4423` TLS version, `S6281` public-access block) | one file's parse tree plus a private per-file symbol table; no dependency, no classpath | **file, no semantics** (structural, not typed) | `specs/analyzers/infrastructure-as-code/specification.md` §2 ("emits no coverage, test-execution data, CPD tokens, public symbol index or dependency graph"), §4.3 (single-file pipeline: parse → visit → emit; Kubernetes is the one family needing cross-file *project* context, still no dependency resolution) |
| 3 | Style, naming, duplication, code-smell rule (the bulk of the 2,418-key catalog we already declined to own) | one file's tokens/parse tree; no semantic model | **file, no semantics** | `docs/specs/2026-08-29-scope-decision.md` §2 ("naming, layout, convention, and deprecated-API mass; delegated to native tooling"), §5 duplication row ("within-repository token-hash detection") |
| 4 | Vulnerable dependency by coordinate | the lockfile alone — the customer's package manager already computed and committed the transitive closure | **declared, no fetch** | `docs/specs/2026-08-29-code-graph-sourcing.md` §5.6 ("A public registry artifact... fetch the declared archive by coordinate and hash from the lockfile... never run a package manager") — note this rung needs *less* than what §5.6 describes for symbol attribution: coordinate-matching against an advisory feed needs no archive fetch at all, only the lockfile's declared coordinates and versions |
| 5 | Single-file taint: source and sink both inside one file, matched against a curated library API model by signature pattern | one file plus a curated model of well-known library sources/sinks; no project-wide type resolution | **file + curated model, no classpath** | `docs/specs/2026-08-29-code-graph-sourcing.md` §5 basis table ("Binding within a file or a scope: scope rules: no [type checker]"); the symbolic-execution kept-capability entry is explicitly "method-local path sensitivity... over one shared intraprocedural framework" (`docs/specs/2026-08-29-scope-decision.md` §5, "Symbolic execution" row) — intraprocedural is the load-bearing word |
| 6 | Cross-file taint or call edges within first-party code | import graph plus scope-local/import-scoped binding; no classpath, no compiler | **import graph, no classpath** | `docs/specs/2026-08-29-code-graph-sourcing.md` §5 ("Cross-file binding where the import graph leaves exactly one reachable candidate — import-scoped name resolution — no [type checker]"); measured concretely: "of the 740 references the grammar-based tool failed on here, 315 are dotted — they carry a qualified prefix that the import graph plus the dependency's own declarations can bind directly" |
| 7 | External symbol attribution: which package a name comes from and its declared signature | dependency declarations plus declarations read out of fetched (public) archives — still no build, no package manager | **declared + fetched declarations** | `docs/specs/2026-08-29-code-graph-sourcing.md` §5 producer table, row 2 ("Grammar parse plus fetched dependency declarations... adds external symbol attribution and signatures... Needs: dependency declarations and reachable artifacts") |
| 8 | Reachability into dependency code, exact overload selection, generic instantiation, inheritance-precise dispatch | a type checker with a classpath — declared archives at rung 1, package-manager-resolved at rung 2 | **type checker + classpath** | `docs/specs/2026-08-29-code-graph-sourcing.md` §5 basis table ("Overload selection, generic instantiation, inheritance-precise dispatch, implicit conversion: type inference over the whole program: yes"); measured cost of *not* having it: "Without a classpath: 57.7% trustworthy, 42.7% of calls, and zero library edges" (§11, JDT spike) |
| 9 | Dependency injection / reflection / service-loader / config-named-class wiring | nothing static resolves the edge; only the *site* is detectable, never the edge itself, at any rung | **undecidable statically — count sites, never guess silently** | `docs/specs/2026-08-29-code-graph-sourcing.md` §5.3 ("A runtime-wired edge is an unknown unknown... The store therefore needs a third honesty channel... runtime-wiring sites") |

Rungs 1–3 collapse to one cost class ("file, no semantics") because none needs anything beyond the single file under examination — the distinction between them is rule *content*, not rule *cost*. Rungs 8 and 9 are the only ones this repository has already conceded need a classpath or are permanently unreachable; everything in between (rungs 4–7) is reachable from a checkout at rest with **zero** fetch (4, on lockfile coordinates alone) up through fetched-but-uncompiled public declarations (7).

## 3. Mapping the five goals onto the ladder

| Goal | What it actually asks | Rung(s) it needs | Evidence it doesn't need more |
|---|---|---|---|
| 1. Analyze source code | Parse, measure, classify files | 1–3 | Every analyzer spec read (text-and-secrets, infrastructure-as-code) performs this with no dependency or classpath input at all |
| 2. Find flaws where they exist | Secrets, IaC misconfig, style/smell, single-file bugs, vulnerable dependency by coordinate, single-file taint, **and** the smaller set of bugs needing checked types (null deref on a checked type, deprecated-API calls into a resolved dependency) | 1–7 for the overwhelming majority; **8 only for the checked-type subset** | `docs/specs/2026-08-29-code-graph-sourcing.md` §5.7 names the split directly: "Consumer one: deterministic findings... a rule needing checked types stays silent when only `declared` or `import-scoped` facts exist" — the rule catalog itself gates by basis, so goal 2 is not one rung, it is a *distribution* across 1–8 with rung 8 reserved for a minority of rules |
| 3. Suggest fixes and improvements | A location plus a range plus (often) the same evidence goal 2 already gathered | same distribution as goal 2 | `docs/specs/2026-08-29-scope-decision.md` §4 keep row: "the flows are the evidence goal 3 needs" — no new rung, it rides goal 2's evidence |
| 4. Understand the codebase | Declarations, import graph, who-calls-what within first-party code, orientation for a reviewing model | **6–7**, explicitly *not* 8 | `docs/specs/2026-08-29-code-graph-sourcing.md` §5.7: "Consumer two: orientation... Recall and honesty outrank precision for this consumer... Orientation must be cheap and always available. It sits on the critical path of every review, so it belongs at rung 1 by construction" — rung 1 in that document's own numbering is *our* rungs 1–7 combined (everything not needing a compiler); the document is explicit that orientation never needs rung 8 |
| 5. Understand blast radius of a change | Transitive reachability over first-party code, with unresolved and runtime-wired edges counted, not silently dropped | **6–7 for the graph, 9 for the honesty channel** | `docs/specs/2026-08-29-scope-decision.md` §3: "Goals 4 and 5 are join-and-reachability questions"; `docs/specs/2026-08-29-code-graph-sourcing.md` §5.6: "It buys almost nothing for the orientation consumer of section 5.7, which needs to know which files a change reaches — and reachability runs through first-party code" — i.e., private-dependency resolution (rung 8, gated behind credentials we refuse) is close to irrelevant to goal 5, because blast radius mostly propagates through code we already parse |

**The compact form of the finding:** goals 1–3 spend most of their mass on rungs 1–3 (no semantics at all) with a long, thin tail reaching rung 8 for a minority of high-value bug classes (~400 of 2,418 rule keys per `docs/specs/2026-08-29-scope-decision.md` §2). Goals 4 and 5 — the ones this repository calls "join-and-reachability" and treats as requiring a resolved symbol graph — actually bottom out at rung 7, one rung short of a type checker, because reachability through first-party code needs only the import graph, and external-symbol attribution needs only fetched public declarations, never compilation. Rung 8 (classpath + type checker) buys *precision inside dependency code*, which neither goal 4 nor goal 5 asks for; it buys it for the *minority* of goal-2/3 findings that need checked types. **No goal in this product needs rung 8 to function at all — rung 8 only raises precision on a bounded, already-identified subset of goal 2 and 3 findings.** This matches CodeRabbit's own observed behavior exactly: it installs dependencies (crossing into what we call rung-2 territory) yet still ships type-aware TypeScript rules disabled and Java deep analysis off by default (`docs/specs/2026-08-29-coderabbit-approach.md`, "What runs" section) — it reaches rung 8's *inputs* opportunistically but does not spend them, because none of its own review questions require it either.

## 4. Where our own documents assume a higher rung than the goal requires

Three concrete over-assumptions found by re-reading the cited sections against the ladder in §2:

1. **`docs/specs/2026-08-29-scope-decision.md` §3, "Architecture consequence" table** originally framed goals 4 and 5 as needing "recursive queries over symbol and reference tables" without qualifying that the *symbols* in that table are overwhelmingly rung-6/7 facts (import-scoped, declared) rather than rung-8 (checked) ones. The table reads as if the store's value depends on compiler-grade symbols; §7 of the same document ("Cross-file resolved symbol identity" gap) reinforces this framing by describing the missing capability only as "resolved symbol identity" with no rung attached. **Correction already made, but not by this document** — `docs/specs/2026-08-29-code-graph-sourcing.md` §5 ("Correction, and it matters more than the trim it follows") explicitly retracts the equivalent error made in *that* document's own first draft: "writing it made me collapse 'no compiler-backed resolver for language X' into 'no semantic route for language X'. That inference is wrong." The scope decision predates that correction and was never itself amended to say so; a reader of `docs/specs/2026-08-29-scope-decision.md` §3 and §7 alone, without the later document, still comes away thinking goals 4–5 need a resolved (rung-8) graph.

2. **`docs/specs/2026-08-29-scope-decision.md` §2, "Headline result" and §11** cost `platform/code-graph` as the largest surviving part and justify that size by "one emitter per language analyzer" (per `docs/specs/2026-08-29-code-graph-sourcing.md`'s own "Amends" line). That per-language-emitter framing is a rung-8 framing — it assumes every language needs a bespoke compiler-backed producer to be useful for goals 4–5. §10 of `docs/specs/2026-08-29-code-graph-sourcing.md` revises the cost to Medium precisely because rungs 6–7 (import graph, fetched declarations) turn out to cover "every language... today", leaving rung 8 as an opportunistic bonus. **This is a self-correction the sourcing document already made**; the residual risk is that anyone reading the scope decision's original cost table in isolation still inherits the rung-8 assumption it was built on.

3. **`docs/specs/2026-08-29-code-graph-sourcing.md` §5.1, "The Java measurement transfers furthest"** itself flags its own earlier over-assumption: the 99.998%-resolution number was obtained by *invoking the target's build tool* (rung 2 in that document's numbering — dependency resolution in a sandbox), yet an earlier framing "called itself build-free, which is true about compilation and false about execution." The document catches this ("What decides the product's actual fidelity is the rung-1 path underneath it... That is the number to measure first") but as of this writing that rung-1-only number is still recorded as unmeasured (§5.1: "remains the load-bearing unmeasured question", carried into §11's list of unmeasured items). **This is a live gap, not a historical one**: the headline Java fidelity claim (99.998%) sits at ladder rung 8 obtained via rung-2 machinery, while the number that actually describes what every customer gets — rung 7, declarations plus cached/fetched archives, no package manager — has not been measured at all. Until it is, any claim that Java analysis is "checkout-at-rest ready" is citing a number from one rung higher than the guarantee the product makes.

No fourth over-assumption was found in the text-and-secrets or infrastructure-as-code specifications — both were already scoped, correctly, to rung 1–3 with no dependency or classpath input claimed anywhere in either document.

## 5. What this means for a checkout-at-rest product

The mis-framing our scope decision fell into was comparing *inputs* (does the vendor install dependencies? run shell commands?) rather than *outputs* (which question does each rule or feature actually answer, and what does answering it honestly require?). CodeRabbit's own documentation shows the same conclusion from the vendor side: it reaches rung 2 (dependency installation) yet ships with rung-8 precision *turned off by default* in its two capable tools — TypeScript type-aware ESLint rules and Java's Infer — because "Java analysis may require compiling more than the changed files" is a cost they decline to pay even with the classpath in hand (`docs/specs/2026-08-29-coderabbit-approach.md`, "Three tools are the exceptions that prove the rule"). They built the elevator to rung 8 and mostly ride it to rung 6.

The corrected framing this ladder makes explicit: **rank rules and features by the rung their own question requires, not by the rung a competitor's sandbox happens to reach.** Under that ranking, the overwhelming majority of goal-2/3 value (rungs 1–3, plus rung 4's free lockfile-coordinate matching) needs no semantics of any kind; goals 4 and 5 — the ones we assumed forced a symbol graph — bottom out one rung short of a type checker (rung 7); and rung 8 is reserved for a bounded, already-named minority of deterministic bug classes, which is exactly what our own kept-capability list already says (`docs/specs/2026-08-29-scope-decision.md` §4, "~400 of 2,418 keys"). The scope decision's `platform/code-graph` design is not wrong under this reading — its basis-tagged, rung-recording model (`docs/specs/2026-08-29-code-graph-sourcing.md` §9, item 1) is precisely the mechanism that lets each rule or query declare which rung it needs and go silent rather than guess when that rung isn't reached. What was wrong was treating the ladder's top rung as the thing to build toward, instead of treating rung placement as a routing decision made once per question, most of which never leave rung 3.
