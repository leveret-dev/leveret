**One-line answer:** CodeRabbit clones the repository into a short-lived, isolated cloud sandbox, installs the target's own dependencies there, runs 59 catalog linters/SAST tools plus LLM-written shell and Python scripts against the live checkout, and explicitly documents that it "can execute shell commands" — it is not a rung-1 product in our sense; it is a rung-2/3 sandbox-execution product that happens to default most of its tool catalog to source-only analysis.

## How it gets the code

Installation is a Git-platform app (GitHub/GitLab/Bitbucket/Azure DevOps) registering webhooks for PR events; no build integration is requested at install time (`our-security-posture...`, Sep 14 2025). On each triggered review, CodeRabbit "clones your repo and keep[s] it in a sandbox" (`context-engineering-ai-code-reviews`, Jul 17 2025), reading it from an in-memory volume mount inside a Cloud Run instance (`cloud.google.com` GCP blog, Apr 23 2025 — infra detail, may have changed since). The clone plus its **installed dependencies** can be cached as a "reusable sandbox cache" for up to seven days to speed later reviews; caching is on by default and optional to disable (`reference/caching`). Separately, CodeRabbit also stores encrypted "vector representations of code" — a persistent semantic/embeddings index used for retrieval across reviews — with no stated retention window found (`faq`, "Code Storage" tab). A third artifact, the "code graph" of definitions/references, is explicitly **not** persisted: "Every time a new review is triggered, CodeRabbit builds a graph representation of code dependencies. These are re-generated each time" (`context-engineering-ai-code-reviews`). So: ephemeral clone-and-install per review, a short-lived (≤7 day) reusable cache of that clone, and a longer-lived embeddings index — three different lifetimes for three different artifacts, all customer-encrypted and independently opt-outable (`reference/caching`; `knowledge-base/index`).

## What it runs

The documented catalog is 59 tools (`tools/reference`, Aug 24 2026). Almost all operate on source or config text alone: **ast-grep** (AST pattern matching, essentials package, source only, skips files ≥8 MiB), **Semgrep/OpenGrep** (pattern rules across 17+ languages, source only), and ~45 single-purpose linters/formatters/scanners — PMD, detekt, RuboCop, Clippy, SwiftLint, Pylint, Flake8, Ruff, PHPCS, PHPMD, Cppcheck, Clang-Tidy, ShellCheck, TFLint, Checkov, Trivy, Hadolint, actionlint, zizmor, Buf, SQLFluff, Squawk, Stylelint, HTMLHint, YAMLlint, markdownlint, LanguageTool, Vale, and the secret/PII scanners Betterleaks, TruffleHog, Presidio, plus OSV-Scanner (reads manifests/lockfiles, not code) — none of which is documented as needing a compiled build.

Three tools are the exceptions that prove the rule:
- **ESLint** — CodeRabbit installs the repository's own declared ESLint dependencies inside the sandbox via `npm`/`yarn`/`pnpm` ("CodeRabbit scans ESLint config files before any npm/yarn/pnpm installs and only permits a curated allow-list of plugins," `tools/eslint`), then runs a curated plugin allow-list. But it explicitly does **not** run `tsc`: "For `@typescript-eslint`, linting with type information is not supported at the moment. The type checking rules… are disabled." Dependency installation happens; type checking is switched off on top of it.
- **golangci-lint** — "run… in a sandbox with `--out-format=json` and per-module scoping. No plugins or external binaries are loaded" (`tools/golangci-lint`). The doc does not itself state whether Go module resolution (`go mod download`) runs first; the company's own architecture post claims the sandbox generally "set[s] up a build environment with necessary dependencies (think npm install, go mod download, etc.)" (GCP blog, Apr 2025, unconfirmed by the current per-tool page).
- **Infer** for Java is **disabled by default**, and the stated reason is explicit: "Disabled by default because Java analysis may require compiling more than the changed files" (`tools/reference`). This is CodeRabbit's own admission that its one Java tool capable of deeper analysis needs build-adjacent compilation, and it opts out by default rather than compile.

No `.NET`/Roslyn analyzer, no Checkstyle/SpotBugs/ErrorProne, and no dedicated Java or Kotlin type-checker beyond PMD (pattern-based) and the disabled Infer path appear in the catalog at all.

Beyond the fixed catalog, the sandbox itself executes model-generated code: the FAQ states plainly that "CodeRabbit Code Reviews" "**Can execute shell commands** and perform deep static analysis against your codebase" (`docs.coderabbit.ai/faq`, current). The GCP post details this as an agent that "creates shell scripts to navigate the code, search for specific patterns (using tools like `cat`, `grep`, and even `ast-grep`)… can even generate Python code," and separately "generat[es] and executing `curl` commands" to call Slack/Jira/Linear (GCP blog, Apr 2025). The Sept 2025 posts confirm the sandbox persists in the current architecture: it runs "tools, linters, web search queries & verification checks," with "internal network access… blocked" but outbound internet allowed (`our-security-posture...`), and web search is a documented, on-by-default, opt-out-able feature (`knowledge-base/web-search`). **This runs on CodeRabbit's own infrastructure** (Cloud Run for the SaaS product); nothing here runs on the customer's CI.

## What the customer must or may change

**Required:** nothing beyond installing the Git-platform app and granting it PR/webhook access. "Zero config to start: just open a PR and get the results!" (`overview/pull-request-review`). Self-hosted Enterprise additionally requires standing up CodeRabbit's own container in the customer's infrastructure and pointing it at a Git platform and an LLM provider (`self-hosted/overview`) — still not a build or CI hook.

**Recommended:** a version-controlled `.coderabbit.yaml` (or an org-wide `coderabbit` central-config repo) for path filters, path-based review instructions, a review profile (`chill`/`assertive`, which changes analysis depth — e.g. PHPStan level 3 vs. 8), and per-tool `config_file` pointers so CodeRabbit uses the customer's own linter configuration (ESLint, golangci-lint, PHPStan, Semgrep, SQLFluff, PMD, detekt, SwiftLint all expose this). ESLint additionally asks that "all ESLint dependencies are defined in your `package.json`" so the sandbox can install them (`tools/eslint`).

**Optional:** enabling `Infer`'s Java mode explicitly (`enable_java: true`), which is an opt-in trade of build-adjacency for depth, since CodeRabbit's own doc warns it "may require compiling more than the changed files"; Multi-Repo Analysis (manual or, on Pro+/Enterprise, automatic cross-repo linking); MCP server connections for internal docs/tickets; disabling the sandbox cache (`reviews.disable_cache`) or opting out of all knowledge-base retention (`knowledge_base.opt_out`).

**Never asked for:** a CI step, a build plugin, or a generated build artifact as a review input. No documented feature ingests a customer-produced SARIF/SCIP/coverage artifact from their own build.

## Where its fidelity ceiling sits

Judged on our axis — declarations, import graph, scope-local binding, declared types, comment-declared types, checked cross-file resolution, runtime wiring:

- **Declarations and import graph:** claimed and demonstrated. The "code graph… analyzes definitions of code symbols… and uses those definitions to enhance context" (`context-engineering-ai-code-reviews`); "a lightweight map of definitions and references" plus commit co-change signal (`how-coderabbit-delivers-accurate-ai-code-reviews-on-massive-codebases`). Rebuilt fresh per review, not persisted.
- **Scope-local binding, declared types, comment-declared types:** no structured extraction is documented anywhere in the corpus retrieved; these appear to be handled implicitly by the LLM reading source text rather than by a typed extraction pass. `[INFERENCE]`
- **Checked cross-file resolution:** explicitly **not** reached by design in the flagship case (TypeScript type-aware ESLint rules disabled) and **not** reached by default in the one tool built to reach it (Infer/Java, off by default). No tool in the 59-tool catalog runs a compiler or type checker over the full project.
- **Cross-repository/repository-wide claims:** made extensively ("reasons across files, not just lines") and backed by two concrete, evidence-labeled mechanisms rather than marketing adjectives alone: a per-review definitions/references graph, and **Security Blast Radius** (open beta), whose relationships (call, import, dependency, read/write, publish/subscribe, test) each carry "confidence" and cite supporting code ranges, but which self-reports as incomplete — "Showing N of M graph candidates," and "an absent component… does not prove that no dependency or downstream impact exists" (`security-agent/blast-radius`). This is retrieval-plus-evidence, explicitly not sound or complete, unlike a compiler-verified graph.
- **Runtime wiring** (DI, reflection, service loaders): not addressed by any documented tool or feature.
- **Caps that bound fidelity regardless of mechanism:** 150–300 files reviewed per PR depending on plan, counted after path-filter exclusion, with reviews over 300 files unsupported even via paid overage (`management/plans`); individual files ≥8 MiB skipped by ast-grep (`tools/ast-grep`); per-developer PR/IDE/CLI rate limits of 5/10/12 per hour by plan, with usage-based fair-usage throttling above the 95th percentile of recent activity (`management/plans`).

## What this means for Leveret Inspect

CodeRabbit does not contradict our checkout-at-rest trim so much as demonstrate the alternative we deliberately rejected: it buys cross-file plausibility by executing target-adjacent code (dependency installs, agent-written shell/Python, `curl` calls) inside an isolated sandbox it fully controls, rather than by adding a compiler frontend. That is a legitimate product shape, but it is rung 2–3 on our own ladder, not rung 1 — it validates that our stricter guarantee (never install, never execute) is a real, chosen trade-off against a shipping competitor, not an oversight. The one technique worth adopting is orthogonal to execution: an evidence/confidence-labeled relationship graph (their Security Blast Radius) is structurally close to our own per-edge basis vocabulary, and their explicit non-claim of soundness ("does not prove no dependency exists") is the same honesty discipline our unresolved-reference and runtime-wiring-site channels already commit to. Their own admission that deep Java analysis needs a build they choose to skip by default (Infer) is independent confirmation of the exact cliff our JDT/rung-1-classpath work is trying to climb without one.
