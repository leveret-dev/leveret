## 1. Snyk Open Source (SCA): per-ecosystem build requirement

Primary table, verbatim from the CLI-build-requirement doc:

| Ecosystem | Build required? | Mechanism | Doc |
|---|---|---|---|
| npm | Only if no `package-lock.json` | parses lockfile; without one, falls back to reading installed `node_modules` (CLI) or approximates the tree (SCM) | `.../open-source-projects-that-must-be-built-before-testing-with-the-snyk-cli`, `.../supported-languages-list/javascript` |
| pnpm | Only if no `pnpm-lock.yaml` | parses lockfile | same |
| Yarn | Only if no `yarn.lock` | parses lockfile | same |
| **Maven** | **Yes, always** — `mvn install` before testing | shells out to Maven and inspects **`mvn dependency:tree`**-style reactor output; requires the local `.m2` repo populated | `.../snyk-cli-for-java-and-kotlin` |
| **Gradle** | No | shells out to Gradle (`gradle build --no-daemon` under the hood) and inspects the resolved `compileClasspath` configuration; needs `--all-sub-projects` / `--init-script` for multi-module and Android variant builds | same |
| .NET NuGet | Only if no `packages.config` (legacy). Modern SDK-style: **"Snyk uses the build system to determine which dependencies are installed"** — `package-lock.json`-equivalent (`project.assets.json`) is generated by `dotnet restore`, which Snyk drives itself for SCM but the CLI needs a prior restore | `.../supported-languages-list/.net` |
| .NET Paket | Yes | `paket.lock` must exist | build-requirement table |
| pip | Yes — `pip install -r requirements.txt`, or `--skip-unresolved=true` to test only what's already resolvable without a build | requirements.txt has no transitive-dependency information at all | build-requirement table |
| pipenv | Yes — `pipenv update` | | same |
| setup.py | Yes — `pip install -e .` | | same |
| Poetry | Only if no `poetry.lock`; run `poetry lock` to generate one. **With a lockfile, no native tooling runs at all** — "Poetry files contain sufficient information to build a full dependency tree without running native tooling" | `.../supported-languages-list/python` |
| **Go Modules** | **No** — but not purely lockfile-based either: Snyk shells out to **`go list -json -deps ./...`** (a Go-toolchain command) plus reads the `go.mod` `toolchain` directive; needs a local Go install, not merely a `go.sum` parse. SCM default path instead parses `go mod graph` textually | `.../supported-languages-list/go` |

| Swift/Obj-C Cocoapods | Only if no `Podfile.lock` | | same |
| Swift SPM | No | | same |
| Scala sbt | No | | same |
| Ruby Bundler | Only if no `Gemfile.lock` | | same |
| PHP Composer | Only if no `composer.lock` | | same |
| **C/C++ (`--unmanaged`)** | **No manifest of any kind, ever** — no package manager to invoke. Snyk hashes every file under the scanned directory and matches the hash set against a database of **official upstream release archives**, at a reported **confidence score** (0–1, based on % of files matching known-release hashes). Requires the dependency's **unpacked source code physically present** in the scanned tree — vendored, not merely declared. Fails silently on heavily modified vendored copies, missing files, or symlink-mangled Windows checkouts | `.../supported-languages-list/c-c++` |

**What "no lockfile" degrades to, precisely:** for npm specifically, CLI/IDE fall back to reading `node_modules` (so *some* install is still implicitly required); SCM instead **approximates** the tree "insights into Projects in development or what the next build will look like" — an explicitly probabilistic, non-authoritative substitute, not a refusal.

**`--unmanaged` beyond C/C++:** Java also exposes `--scan-unmanaged` / `--scan-all-unmanaged` for bare JAR/WAR/AAR files with no build file at all, auto-detecting archives recursively — same "no manifest, fingerprint what's there" philosophy as C/C++, but keyed on Maven-coordinate-embedding conventions inside the JAR rather than whole-tree file hashing.

## 2. Snyk Code (SAST): what it actually builds, and whether it resolves dependency types

**Lineage confirmed:** Snyk Code is DeepCode (ETH Zurich spin-off, Raychev/Vechev/Paskalev, acquired by Snyk 2020) (`snyk.io/blog/advanced-technologies-behind-snyk-code/`).

**Program representation (from Snyk's own technical docs, not marketing):** the pipeline parses source into an **AST**, then into an **"event graph" (EG)** — "two node types... some represent parts of the code, and others represent how the code is used" — which is language-agnostic in shape and "capable of representing various programming languages." A **proprietary logic solver** (explicitly compared to, and claimed faster than, "standard Datalog solvers") runs curated rules against the EG to find matches; ML is used to **mine which source/sink/sanitizer patterns to encode as rules** from a training corpus of open-source commits, not to make the runtime detection decision itself (`snyk.io/blog/advanced-technologies-behind-snyk-code/`; `docs.snyk.io/supported-languages/technical-specifications-and-guidance` §"How Snyk Code analysis works").

**Does it resolve dependency types across a compile boundary? No evidence it does, and structural evidence it cannot:**
- The documented pipeline is *parse → event graph → rule match*. No step reads a classpath, a `node_modules` tree, or any dependency archive. Snyk Code explicitly needs **no build**: "Snyk does not require compilation or a build to perform analysis. Snyk Code analyzes the source code directly. If you have precompiled components, ensure the source code is available during the scan" — stated for C/C++, but the same 1 MB-file/UTF-8/`.gitignore`-driven ingestion pipeline is described language-generically (`docs.snyk.io/.../c-c++`; `docs.snyk.io/scan-fix-and-prevent/scan-with-snyk/snyk-code`).
- The "AI Engine" feature list names "type inference" as a capability, glossed explicitly as "of special interest for **dynamically typed languages**" — i.e. inference over syntax/usage patterns within the analyzed source, not classpath-resolved binding to a library's actual declared types.
- **Framework support is enumerated per-library, by name, and explicitly gated on training data, not on type resolution:** "To support a specific framework, Snyk Code must both support the relevant language **and be trained on Projects using the framework**. The found patterns are then annotated by the security team and extended by curated content." Two named support tiers: *Comprehensive* ("All relevant sources and sinks are identified") vs. *Partial* ("Coverage may be limited... Potential for false negatives in taint analysis or source/sink identification") (`docs.snyk.io/supported-languages/technical-specifications-and-guidance`). If Snyk Code resolved real dependency types, framework support would be a function of the language's type system, not a per-library curation and training exercise with two named quality tiers.
- Per-language "Supported frameworks and libraries" pages (Java: Spring, Hibernate, Jackson, okhttp3…; JS: express, pg, mongoose…; Python: flask, requests, sqlalchemy…; C/C++: OpenSSL, libpq, SQLite…) are finite, named, curated lists — the direct fingerprint of a **library-model catalog**, structurally identical to Semgrep's or CodeQL's per-framework taint model libraries, not a byproduct of a universal resolved-type analysis.

**Answer to the acceptance-criteria question:** Snyk Code matches **modelled API signatures by name against a curated, per-framework library catalog**, mined from training data and hand-annotated by Snyk's security team. It does not perform classpath/`node_modules`-resolved type binding into third-party code. Interprocedural analysis stops at the boundary of what the curated model encodes as a source/sink/sanitizer for that named library — it does not descend into arbitrary third-party source, because it never has the dependency's source or bytecode in the first place.

## 3. How Snyk Code knows `Statement.executeQuery` is a sink without resolving types

No public rule DSL exists for Snyk Code (unlike Snyk IaC, which ships a documented Rego-based custom-rules SDK — `docs.snyk.io/scan-fix-and-prevent/scan-with-snyk/snyk-iac/current-iac-custom-rules`). Snyk Code's own rules are closed and only enumerated by name/CWE/OWASP-category on the security-rules pages (e.g. `java-rules.md` lists "SQL Injection → CWE-89", "SSRF → CWE-918" etc., with no signature detail exposed). Combined with §2's framework-curation evidence, the mechanism is: **name/signature-pattern matching against a curated per-library model**, populated by (a) ML pattern-mining over historical open-source fix commits and (b) manual annotation by Snyk's security research team (`snyk.io/blog/advanced-technologies-behind-snyk-code/` — "the learning process involves Snyk security engineers that work with machine learning algorithms to generate and maintain the knowledge base"). This is the same category of solution CodeQL and Semgrep use (curated per-library source/sink model libraries), not resolved-type binding. Snyk does not publish the model itself, only its category ("Comprehensive"/"Partial") and CWE coverage.

## 4. Reachability analysis: the one feature that needs real call edges into dependency code

**Coverage (GA unless noted):**

| Language | Package managers | Status | Doc |
|---|---|---|---|
| Java | Maven, Gradle | GA | `.../reachability-analysis` |
| JavaScript, TypeScript | npm, Yarn, pnpm | GA | same |
| Python | pip, Poetry, pipenv | GA (99%+ of applicable vulns per `updates.snyk.io`, Oct 16 2025) | same |
| C# | NuGet, paket | Early Access | same |

**Two structurally different delivery paths, easy to conflate — and this is the informative finding:**
1. **SCM/SaaS import path (GA):** Snyk states this "quickly analyze[s] the code **without requiring the application to be built prior to the scan**" — the DeepCode program-analysis engine builds the call graph from uploaded source plus its resolved dependency graph, using the same event-graph/curated-model machinery as §2, not a compiled classpath.
2. **Snyk CLI path (Early Access, CLI ≥1.1301.0):** per a Snyk support article (only accessible via search-engine cache — see caveat above, `[UNVERIFIED]`), "**To run it using Snyk CLI, you must have the app already built (compiled), and the bytecode of the app should be available.**" This is the sharpest documented instance in this whole investigation of a feature that genuinely needs compiled artifacts, and it is scoped narrowly to the CLI/CI delivery mode, not to reachability as a whole.

**Mechanism, per Snyk's own doc:** (1) enrich known vulnerabilities with their upstream fix commit; (2) DeepCode analysis ranks code elements near that diff as likely root cause; (3) build the caller-side call graph and the dependency-side call graph separately; (4) look for a path between them. Explicitly **security-expert-supervised** ("Snyk security experts will manually verify and mark elements as root causes... over time") — i.e. partly a curated/human-verified overlay on top of the automated graph, not a fully mechanical soundness guarantee.

**Published limitation language (Snyk's own, not ours):**
- "Program analysis requires a trade-off between accurate results, minimizing false positives, and recall rates... Snyk DeepCode analysis applies real-time decision-making to determine whether to **under-approximate** the set of reachable elements."
- Reflection is named explicitly as a case where "it is not always possible to give a precise answer... neither returning a large set of false positives nor returning 'Not reachable' will suffice."
- `NO PATH FOUND` "does not mean that the vulnerability is completely unreachable or unexploitable" — and can flip to `REACHABLE` later purely from **first-party** code or SAST-engine changes, with no dependency change at all.
- Hard technical ceilings: 300,000-file cap, 3 GB combined upload, 1 MB per file, 256-char filenames.
- **No published quantitative precision/recall specific to reachability.** The only independently measured precision/recall figures found are for general Snyk Code SAST detection, not reachability: an independent academic benchmark (10 C# projects, 63 known vulnerabilities) measured Snyk Code at precision 0.686 / recall 0.523 / F1 0.546 — ahead of SonarQube (F1 0.260) and CodeQL (F1 0.386) in that sample, behind GPT-4.1/Mistral/DeepSeek-V3 on recall — and noted Snyk Code "consistently reports a significantly higher number of vulnerabilities... suggesting a more aggressive detection strategy" (`arxiv.org/abs/2508.04448`).

**Why Java leads:** static typing and explicit imports/interfaces let the call-graph matcher bind a call site to a specific class/method with far less ambiguity than duck-typed JS/Python — consistent with §2's finding that the underlying mechanism is signature/pattern matching, which degrades gracefully with typing discipline rather than failing outright without it.

## 5. What Snyk admits it cannot do without help

Direct quotes, not paraphrase:

- **"Before testing your Open Source Project for vulnerabilities, with limited exceptions, you must build your Project."** — stated as the governing rule, not an edge case (`.../technical-specifications-and-guidance`).
- **.NET, hard cliff:** "Snyk does not support `package-lock.json`. Snyk uses the build system to determine which dependencies are installed." No lockfile-only fallback exists for modern NuGet — this is the .NET-family "resolution comes only from the build, or nothing" cliff, independently corroborating our own `docs/specs/2026-08-29-code-graph-sourcing.md` §9 finding about .NET.
- **Maven, hard cliff, no fallback documented other than partial data:** "Run `mvn install` before testing" is listed with **no** "if no lockfile" escape hatch (Maven has no lockfile format at all) — the only degradation path is `--skip-unresolved=true`, explicitly "will not capture the full dependency tree with nested dependencies."
- **Gradle Android build variants can fail the scan outright** with a Gradle-native error ("Cannot choose between the following configurations...") rather than degrade — requiring the customer to hand-pick a `--configuration-matching` regex.
- **C/C++ unmanaged matching fails silently** on: unofficial/unreleased source, source modified beyond a confidence threshold, partial vendoring, symlink-mangled cross-platform checkouts, and freshly published components (database refreshed only twice a month).
- **Reachability's own hedge language** (§4) is Snyk's explicit admission that static reachability is inherently incomplete, not a bug to be fixed.

## What this means for a checkout-at-rest product

Snyk's own architecture is the strongest evidence available that our rung-1 trim is the right one, not a compromise: its **flagship, highest-volume products (SCA lockfile parsing, Snyk Code SAST) are source/manifest-only by construction**, and the one place Snyk genuinely needs compiled artifacts (CLI-mode reachability) is Early Access, narrowly scoped, and layered as a bonus on top of a GA feature that already works without a build. Snyk Code in particular validates our own §5 (code-graph-sourcing spec): a curated, per-library signature model is a legitimate, shippable way to answer "is this a sink" without ever resolving a dependency's real type — it trades soundness for breadth, exactly the trade our own `name-matched`/`declared` basis tiers are built to represent honestly. The one caution: Snyk's Maven and .NET paths show that "SCA needs a build" is not a myth confined to two obscure ecosystems — it is the default posture for two of the most common enterprise stacks, and Snyk's answer is a documented, lossy fallback (`--skip-unresolved=true`) rather than a refusal, which is the shape our own rung-1/degraded-result behavior should mirror rather than the all-or-nothing .NET analyzer pattern.
