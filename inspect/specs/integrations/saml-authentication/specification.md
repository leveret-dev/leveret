## 2. Purpose, scope, and exclusions

The integration acts as one SAML 2.0 relying party, identified internally by provider key and registration ID `saml`. It initiates authentication requests through an asserting party's Single Sign-On URL, accepts SAML responses at the product callback, validates signatures and assertions, optionally signs requests and decrypts responses, rejects replayed response IDs, maps assertion attributes to an external user identity, and hands that identity to platform identity access. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlIdentityProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RedirectToUrlProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlResponseAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java` in the same package]

The scope also includes the administrator-only SAML configuration validation flow because it emits protocol requests, consumes real SAML responses, and exposes mapping and cryptographic status. [Sources: `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationInitAction.java`; `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationAction.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/SamlValidationRedirectionFilter.java`]

Local user creation and update, local group application, session and token creation, cookie handling, CSRF-state storage, return-page policy, authorization, and permissions belong to `platform/identity-access/`. Generic route dispatch and error-page formatting belong to `platform/http-api/`. Relational storage and transactions belong to `platform/persistence/`. This specification describes only the SAML-facing inputs and the identity result passed to those owners. [Source: `manifest/dependency-map.md`]

The pinned integration does not implement SAML Single Logout, service-provider metadata publication, asserting-party metadata import, IdP discovery, SAML artifact binding, multiple SAML providers, multiple verification certificates, certificate-rollover sets, SCIM provisioning, or periodic identity synchronization. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlIdentityProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlSettings.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlModule.java` in the same package]

## 4. Public identity, routes, and outputs

The identity-provider key is `saml`. Its display name is configurable and defaults to `SAML`; its login-page display uses `/images/saml.png` on background color `#444444`. The provider declares that first-login registration is allowed. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlIdentityProvider.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

Protocol-relevant routes are:

| Path | Role | Method behavior |
|---|---|---|
| `/sessions/init/saml` | Normal service-provider-initiated login | Platform authentication filter invokes SAML initialization and returns an HTTP redirect to the configured asserting-party login URL. |
| `/oauth2/callback/saml` | Normal assertion consumer callback | Relying-party metadata advertises HTTP-POST. The pinned token converter can also decode a GET response, though POST is the supported advertised binding. |
| `/saml/validation_init` | Internal administrator validation start | GET-style internal action. Requires a logged-in system administrator and initiates a SAML request with validation RelayState. |
| `/saml/validation` | Internal administrator validation result | POST-only internal action requiring `SAMLResponse`; verifies a `CSRFToken`, requires a system-administrator session, and returns an HTML status report without registering or logging in the asserted user. |

[Sources: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/InitFilter.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/OAuth2ContextFactory.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/SamlValidationRedirectionFilter.java`; `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationInitAction.java`; `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationAction.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; Spring Security 7.0.5 `Saml2AuthenticationTokenConverter`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/web/Saml2AuthenticationTokenConverter.java]

A successful normal callback outputs a `UserIdentity` containing mapped provider login, name, optional email, and optional group set. It then asks identity access to authenticate the identity and redirect to the originally requested page. Session, JWT, local registration, group application, and safe return-target selection are identity-access outputs, not SAML protocol outputs. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlIdentityProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/OAuth2ContextFactory.java`; `manifest/dependency-map.md`]

## 5. Configuration and defaults

All SAML settings are instance-level authentication settings. Settings ending in `.secured` are registered as password-type values. Platform configuration storage and precedence apply; the integration reads the effective values and adds no request-level override. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlSettings.java`; `manifest/dependency-map.md`]

| Key | Default | Required behavior |
|---|---:|---|
| `sonar.auth.saml.enabled` | `false` | Provider can be offered only when true and every activation prerequisite below is present. |
| `sonar.auth.saml.applicationId` | `sonarqube` | Relying-party entity ID and expected assertion audience; emitted as AuthnRequest issuer. |
| `sonar.auth.saml.providerName` | `SAML` | Human-facing login-provider name. |
| `sonar.auth.saml.providerId` | none | Asserting-party entity ID; exact expected response and assertion issuer. |
| `sonar.auth.saml.loginUrl` | none | Asserting-party SSO destination and HTTP redirect base URL. |
| `sonar.auth.saml.certificate.secured` | none | Single X.509 certificate used as the asserting party's signature-verification credential. |
| `sonar.auth.saml.user.login` | none | Assertion attribute name whose first value becomes external provider login. |
| `sonar.auth.saml.user.name` | none | Assertion attribute name whose first value becomes display name. |
| `sonar.auth.saml.user.email` | absent | Optional assertion attribute name; first value becomes email. |
| `sonar.auth.saml.group.name` | absent | Optional assertion attribute name; all nonnull values become external groups. Absence disables group synchronization output. |
| `sonar.auth.saml.signature.enabled` | `false` | When true, outbound AuthnRequests must be signed and both service-provider key and certificate are required. |
| `sonar.auth.saml.sp.privateKey.secured` | absent | Unencrypted PKCS#8 RSA private key used for response decryption and, when enabled, request signing. |
| `sonar.auth.saml.sp.certificate.secured` | absent | X.509 service-provider certificate paired with the private key for decryption and signing credentials. |

[Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlSettings.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/SamlSettingsTest.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`]

The provider is considered enabled only when `sonar.auth.saml.enabled` is true and effective values are present for application ID, provider ID, login URL, asserting-party certificate, login attribute, and name attribute. Application ID is normally present through its default. Provider name is not part of the activation predicate because it also has a default. Email, group, request signing, and service-provider credentials are optional. The activation check tests presence rather than protocol validity; malformed URLs, certificates, keys, or blank semantic values fail later when a registration or response is processed. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlSettings.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/SamlSettingsTest.java`]

Each login initialization and callback constructs a fresh relying-party registration from current effective settings. The integration does not retain a long-lived registration, parsed certificate, or parsed private key. Changes therefore affect later operations without a module-owned cache, subject to platform configuration delivery. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RelyingPartyRegistrationRepositoryProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationResolver.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`]

## 6. Certificate and private-key handling

The asserting-party certificate parser removes an exact PEM certificate header and footer if present, removes all whitespace, performs basic Base64 decoding, and asks the JVM X.509 certificate factory to parse the result. A bare Base64 DER certificate and a PEM-wrapped certificate are therefore accepted. Malformed Base64 or invalid X.509 data fails registration construction; X.509 parsing failure is classified as an invalid certificate. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlCertificateConverter.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/SamlCertificateConverterTest.java`]

The service-provider private-key parser removes an exact unencrypted private-key PEM header and footer if present, removes whitespace, performs basic Base64 decoding, interprets the bytes as PKCS#8, and constructs an RSA key. PKCS#1, encrypted PKCS#8, non-RSA keys, malformed Base64, and invalid key specifications are not supported inputs. Invalid key specifications fail with a format-oriented configuration error. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlPrivateKeyConverter.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/SamlPrivateKeyConverterTest.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

Exactly one asserting-party verification certificate is registered. Signature verification trusts that configured certificate directly; the pinned Spring Security provider explicitly does not perform PKIX path validation of the configured verification certificate. The product does not configure certificate-chain building, revocation checks, certificate discovery, or a rollover set. Operators must rotate the configured value when the asserting party changes keys. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; Spring Security 7.0.5 `OpenSaml5AuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/opensaml5Main/java/org/springframework/security/saml2/provider/service/authentication/OpenSaml5AuthenticationProvider.java]

Service-provider credential precedence is:

1. If no private key is configured, no signing or decryption credential is registered. A configured service-provider certificate alone is unused. Request signing enabled in this state is a configuration failure. [Source: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`]
2. If a private key is configured, the service-provider certificate is also required. The pair is always registered for decryption. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlSettings.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java` in the same package]
3. If request signing is enabled, the same pair is additionally registered for signing and the asserting-party registration is marked as wanting signed AuthnRequests. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepositoryTest.java`]
4. If request signing is disabled but both service-provider values are present, outbound requests remain unsigned while encrypted responses can be decrypted. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

The integration does not explicitly verify that the service-provider certificate contains the configured private key's public key. A mismatch fails only when the delegated cryptographic operation cannot use the pair successfully. [Source: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`]

## 7. Relying-party registration

Every resolution returns the same logical registration regardless of the registration ID supplied by the caller. Its fields are:

- registration ID `saml`;
- relying-party entity ID equal to `sonar.auth.saml.applicationId`;
- assertion-consumer location equal to the platform-generated public callback URL, normally `<public-root>/oauth2/callback/saml`;
- assertion-consumer binding HTTP-POST;
- asserting-party entity ID equal to `sonar.auth.saml.providerId`;
- asserting-party SSO location equal to the validated `sonar.auth.saml.loginUrl`;
- asserting-party SSO binding HTTP-Redirect, inherited from the pinned Spring registration default;
- one verification credential from the configured asserting-party certificate;
- optional signing and decryption credentials as specified above;
- no NameID format and no logout service. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/OAuth2ContextFactory.java`; Spring Security 7.0.5 `RelyingPartyRegistration`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/registration/RelyingPartyRegistration.java]

The login URL must parse as an absolute URI convertible to a JVM URL. Invalid syntax, a relative value, or an unsupported URL conversion fails with an invalid-login-URL state error. No HTTPS-only check is applied; valid `http://` values are accepted, as demonstrated by pinned tests. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

When a callback URL is unavailable to the registration provider, it substitutes `http://anyurl`. Product login and callback flows supply a real callback URL; the placeholder exists for operations that resolve a registration without one and is not an advertised deployment endpoint. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepositoryTest.java`]

## 8. Authentication-request processing

### 8.1 Normal initiation

When `/sessions/init/saml` selects the enabled provider, identity access supplies the public callback URL and generates a CSRF state. The SAML integration constructs an AuthnRequest and sends an HTTP redirect to the asserting-party login URL. An I/O failure while sending the redirect becomes an unchecked redirect failure. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlIdentityProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RedirectToUrlProvider.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/OAuth2ContextFactory.java`]

The AuthnRequest contains a generated request ID, current issue instant, `ForceAuthn=false`, `IsPassive=false`, issuer equal to application ID, destination equal to login URL, assertion-consumer URL equal to the callback URL, and requested response protocol binding HTTP-POST. No NameID policy is emitted because the registration specifies no NameID format. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationRequestResolver`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/web/authentication/BaseOpenSamlAuthenticationRequestResolver.java]

The XML request is DEFLATE-compressed and Base64-encoded for HTTP-Redirect. The integration appends nonblank `SAMLRequest` and `RelayState` query parameters to the configured login URL, preserving the URL as the redirect base. Parameter names and values are URL-encoded with the pinned implementation's ISO-8859-1 encoding call. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RedirectToUrlProvider.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationRequestResolver`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/web/authentication/BaseOpenSamlAuthenticationRequestResolver.java]

### 8.2 Signed requests

When `sonar.auth.saml.signature.enabled=true`, the HTTP-Redirect query also contains `SigAlg` and `Signature`. The pinned default signing algorithm is `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`. The signature covers the redirect-binding signing parameters produced by Spring Security, including RelayState when present. Missing service-provider key or certificate prevents request creation rather than silently emitting an unsigned request. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RedirectToUrlProvider.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`; Spring Security 7.0.5 `RelyingPartyRegistration`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/registration/RelyingPartyRegistration.java]

### 8.3 Request correlation

The integration does not save the emitted AuthnRequest into Spring Security's SAML request repository. On response validation it deliberately removes response-level `InResponseTo` errors and configures assertion validation to accept the first assertion `SubjectConfirmationData.InResponseTo` value as its own expected value. Consequently, SAML request-ID correlation is not enforced. Normal callback CSRF protection instead depends on the platform-generated `RelayState`, and replay protection depends on the durable response ID. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RedirectToUrlProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlConfiguration.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; Spring Security 7.0.5 `Saml2AuthenticationTokenConverter`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/web/Saml2AuthenticationTokenConverter.java]

## 9. Response input and decoding

The normal callback verifies the platform CSRF state from parameter `RelayState` before decoding or authenticating the SAML response. Identity access refuses to register a returned identity unless that state verification has occurred. A response with valid SAML signatures but missing or invalid RelayState therefore does not create a session through the normal callback. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/OAuth2ContextFactory.java`]

The response value is read from request parameter `SAMLResponse`. For POST, the token converter requires Base64 and decodes the XML without DEFLATE. For GET, the pinned converter also permits the parameter and inflates it after Base64 decoding. Missing or undecodable input yields no usable authentication token or a SAML response error. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlResponseAuthenticator.java`; Spring Security 7.0.5 `Saml2AuthenticationTokenConverter`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/web/Saml2AuthenticationTokenConverter.java]

The callback URL passed to the dynamic registration is the same platform public callback URL used for response `Destination` and bearer-recipient validation. Deployments behind a proxy must therefore configure the platform public root URL so that the value exactly matches the asserting party's response. [Sources: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/OAuth2ContextFactory.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlResponseAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`]

## 10. Response validation pipeline

Processing is synchronous and fails closed. The stages are:

1. Decode and deserialize the SAML XML through the pinned Spring Security 7.0.5/OpenSAML 5.1.6 provider. Malformed XML or incompatible response data becomes a SAML authentication error. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlResponseAuthenticator.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]
2. If the response is signed, verify its signature with the single configured asserting-party certificate. If it is unsigned and contains encrypted assertions, refuse to decrypt them. If it is signed, decrypt response-level encrypted assertions using the service-provider decryption credential. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]
3. Apply default response validation, retaining all errors except `INVALID_IN_RESPONSE_TO`, then apply response-ID replay validation. [Source: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`]
4. Validate every assertion's signature. If the response or assertion is signed, decrypt assertion-level encrypted elements with the service-provider credential. Validate every assertion's conditions and subject confirmation. Errors from any assertion fail the response. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlConfiguration.java`; Spring Security 7.0.5 `OpenSaml5AuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/opensaml5Main/java/org/springframework/security/saml2/provider/service/authentication/OpenSaml5AuthenticationProvider.java; Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]
5. Require either a signed response or signatures on every assertion. A signed response permits unsigned assertions; an unsigned response is acceptable only when every assertion is signed. [Source: Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]
6. Require the first assertion to contain a subject with a NameID. After all assertions validate, Spring Security builds the authenticated principal from the first assertion and exposes that assertion's attributes to SonarQube mapping. [Source: Spring Security 7.0.5 `OpenSaml5AuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/opensaml5Main/java/org/springframework/security/saml2/provider/service/authentication/OpenSaml5AuthenticationProvider.java]

### 10.1 Response checks

The default response checks require a successful SAML status, a response issuer exactly equal to `sonar.auth.saml.providerId`, and at least one assertion. If `Destination` is present and nonblank, it must exactly equal the callback URL. A missing response status or missing status code is treated by the pinned dependency as success; any explicit non-success status is an error. Response-level `InResponseTo` mismatch or absence of a saved request is the only default response error removed by SonarQube. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`; Spring Security 7.0.5 `OpenSaml5AuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/opensaml5Main/java/org/springframework/security/saml2/provider/service/authentication/OpenSaml5AuthenticationProvider.java]

### 10.2 Assertion checks

The assertion validation context expects audience equal to application ID, bearer recipient equal to callback URL, and assertion issuer equal to provider ID. It uses a five-minute clock skew, validates supported temporal and bearer subject-confirmation constraints, applies audience, delegation, and proxy restriction validators, and disables subject-confirmation network-address checking. The dependency's `OneTimeUse` condition validator accepts that condition without its own cache; SonarQube's separate replay guard is keyed to the response ID instead. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlConfiguration.java`; Spring Security 7.0.5 `OpenSaml5AuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/opensaml5Main/java/org/springframework/security/saml2/provider/service/authentication/OpenSaml5AuthenticationProvider.java]

The configured assertion `InResponseTo` expectation is the first nonnull value found in that assertion itself, so it does not correlate to the emitted AuthnRequest ID. Assertion signature verification is performed separately from condition validation and remains mandatory according to the response-or-all-assertions rule. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlConfiguration.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]

### 10.3 Encryption

Encrypted assertions are supported only when the outer response is signed and the service-provider key/certificate pair is configured. Encrypted assertion elements such as encrypted subject identifiers are decrypted when the containing response or assertion has a valid signature. Missing decryption credentials or cryptographic failure aborts authentication; plaintext fallback is not attempted. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]

## 11. Replay protection and persistence

Every response passes its SAML response ID to the durable replay checker. In a new database transaction, the checker first searches for that ID. If found, validation returns error code `response_id_already_used` and authentication fails. If absent, it inserts the ID with expiration equal to checker time plus one day and commits before assertion validation and identity mapping continue. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlMessageIdChecker.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlMessageIdCheckerIT.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

Response-ID persistence occurs whenever the custom response validator runs, even when the default response validator has other errors. The broader Spring pipeline also continues from a response-signature error into response validation, so an invalid response can consume a previously unseen ID before the final error is raised. No ID is rolled back merely because later assertion validation, decryption, attribute mapping, or local registration fails. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlMessageIdChecker.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]

Table `saml_message_ids` stores a generated UUID primary key, nonnull `message_id` up to 255 characters, nonnull expiration timestamp, and creation timestamp. A unique database index on `message_id` enforces cluster-wide uniqueness. The checker performs select then insert rather than one atomic compare-and-set; concurrent first uses can race, but the unique index allows at most one commit. A losing concurrent request fails through persistence rather than necessarily receiving the friendly duplicate error. [Sources: `server/sonar-db-migration/src/main/java/org/sonar/server/platform/db/migration/version/v00/CreateInitialSchema.java`; `server/sonar-db-dao/src/main/resources/org/sonar/db/user/SamlMessageIdMapper.xml`; `server/sonar-db-dao/src/main/java/org/sonar/db/user/SamlMessageIdDao.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlMessageIdChecker.java`]

Expired replay IDs are deleted when expiration is strictly earlier than current platform time. The shared session cleaner runs immediately at web-server start and then every 24 hours, guarded by cluster lock `SessionCleaner`; each cleanup commits separately. An ID therefore remains a replay rejection for at least its one-day lifetime and potentially until the next cleaner run. [Sources: `server/sonar-db-dao/src/main/resources/org/sonar/db/user/SamlMessageIdMapper.xml`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/purge/ExpiredSessionsCleaner.java`; `server/sonar-webserver-auth/src/it/java/org/sonar/server/authentication/purge/ExpiredSessionsCleanerIT.java`]

## 12. Principal and identity mapping

Spring Security requires a subject NameID in the first validated assertion even though SonarQube does not use that NameID as provider login. It exposes the first assertion's attribute map. For supported XML scalar types, values become corresponding Java values; SonarQube then obtains textual identity values with each value's string representation. [Sources: Spring Security 7.0.5 `OpenSaml5AuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/opensaml5Main/java/org/springframework/security/saml2/provider/service/authentication/OpenSaml5AuthenticationProvider.java; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`]

Mapping rules are:

- Login is the first value of the attribute named by `sonar.auth.saml.user.login`. Missing or null value fails with a mapping error naming that configured attribute. [Source: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`]
- Name is the first value of the attribute named by `sonar.auth.saml.user.name`. Missing or null value fails likewise. [Source: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`]
- Email is optional. When an email attribute is configured and present, its first value's string form is used; a missing, null, or empty value produces no email. Additional email values are ignored. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/PrincipalToUserIdentityConverterTest.java`]
- Groups are optional. When a group attribute is configured and contains at least one nonnull value, all values' string forms become a deduplicated unordered set and group synchronization is requested. Missing, null-only, or empty group values attach no group set and do not request synchronization. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/PrincipalToUserIdentityConverterTest.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

The resulting provider login and display name are mandatory at this boundary. There is no fallback from a missing mapped login or name to NameID or another assertion attribute. Mapping is exact-name and case-sensitive according to the principal's attribute map. Local account linking, collision handling, group existence, and authorization remain identity-access contracts. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`; `manifest/dependency-map.md`]

## 13. Redirect and state behavior

The initial redirect target is the configured login URL with generated SAML query parameters. The integration does not restrict that URL to HTTPS, same-origin destinations, or an allowlist. A valid administrator-configured URL is trusted. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RedirectToUrlProvider.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

Identity access reads its stored return target, deletes authentication parameters, and redirects to that target or to the server context root when absent. Return-target validation and session creation remain owned by identity access. ## 14. Administrator validation flow

A system administrator can start validation at `/saml/validation_init`. The action verifies administrator status, generates platform CSRF state, and initiates the ordinary AuthnRequest with RelayState `validation-query/<state>`. If request construction fails with an argument or state error, it redirects directly to `/saml/validation?CSRFToken=<state>` so the validation surface can report failure rather than beginning an external login. [Source: `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationInitAction.java`]

When the asserting party posts back to `/oauth2/callback/saml` with validation RelayState, a dedicated filter intercepts the callback before ordinary authentication. It recognizes the `validation-query` prefix and a nonempty token, HTML-escapes `SAMLResponse` and the token, and returns a nonce-protected HTML page that automatically POSTs both values to `/saml/validation`. Other RelayState values continue through the normal callback chain. [Sources: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/SamlValidationRedirectionFilter.java`; `server/sonar-webserver-auth/src/main/resources/validation-redirection.html`]

The validation action verifies `CSRFToken`, then independently requires an active system-administrator session. It replaces the apparent request URL with the normal public SAML callback URL for destination and recipient validation, performs the complete response authentication and replay flow, but does not call the platform identity-registration callback. Its HTML report contains status, all available assertion attributes, configured attribute mappings and values, mapping errors, optional-mapping warnings, and booleans for configured request signing and detected encrypted assertion presence. [Sources: `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationAction.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlStatusChecker.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticationStatus.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthStatusPageGenerator.java` in the same package]

Missing or empty mandatory login/name mappings make validation status `error`. Missing optional email/group mappings become warnings only when mandatory mapping has no errors. The report's `signatureEnabled` value describes outbound request-signing configuration, not whether the received response was signed. Its `encryptionEnabled` value is detected by Base64-decoding the raw response and looking for an encrypted-assertion element; it is a presentation observation, while actual decryption success is established by the authentication pipeline. [Source: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlStatusChecker.java`]

Both validation HTML responses set `Content-Security-Policy`, `X-Content-Security-Policy`, and `X-WebKit-CSP` with a fresh 130-bit random nonce. The policy restricts default content to self, disables base and object sources and workers, permits only nonce-bearing scripts, permits self and inline styles, and allows the listed image, font, and connection sources. The validation result contains assertion attributes and is therefore restricted to administrator plus CSRF checks. [Sources: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/SamlValidationCspHeaders.java`; `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationAction.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/SamlValidationRedirectionFilter.java`]

A validation response consumes its replay ID exactly like a login response. Reposting the same SAML response, or attempting to use it afterward for normal login, is rejected while the ID remains stored. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlMessageIdChecker.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

## 15. Lifecycle and concurrency

The SAML provider and its collaborators are server-side singleton services, but relying-party registrations and protocol authentication tokens are operation-local. Effective settings are read when registrations are created. Replay state is the only SAML-owned durable state. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlModule.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RelyingPartyRegistrationRepositoryProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationResolver.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlMessageIdChecker.java` in the same package]

Concurrent callback processing uses independent parsing and validation objects around a shared authentication provider and shared configuration service. Replay coordination is database-wide through the unique message-ID index, and cleanup coordination is cluster-wide through the shared cleaner lock. There is no in-memory replay cache, per-user lock, protocol queue, asynchronous validation, or partial authentication state. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlResponseAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlMessageIdChecker.java`; `server/sonar-db-migration/src/main/java/org/sonar/server/platform/db/migration/version/v00/CreateInitialSchema.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/purge/ExpiredSessionsCleaner.java`]

## 16. Failure, partial-result, and recovery behavior

- Missing activation prerequisites make the provider unavailable rather than partially enabled. Direct use of a missing required getter fails with a setting-specific argument error. ## 17. Security and trust boundaries

The administrator-configured provider ID, login URL, asserting-party certificate, service-provider private key and certificate, and attribute names are trusted configuration. Assertion contents, RelayState, SAMLResponse, response IDs, attribute values, and redirect callbacks are untrusted network inputs until their relevant checks pass. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlSettings.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`]

HTTPS is not enforced for the asserting-party login URL. Production deployments must configure an HTTPS URL and a public HTTPS callback at the platform boundary to protect request, response, and RelayState confidentiality and integrity outside XML signatures. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

The configured asserting-party certificate is a direct signature-verification credential rather than a PKIX trust anchor subject to chain and revocation validation. Secure configuration storage and access control for `.secured` values are platform responsibilities. The private key is parsed in process memory on registration creation and is never emitted in protocol output. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlCertificateConverter.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlPrivateKeyConverter.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; Spring Security 7.0.5 `OpenSaml5AuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/opensaml5Main/java/org/springframework/security/saml2/provider/service/authentication/OpenSaml5AuthenticationProvider.java]

Normal authentication requires RelayState CSRF verification and durable response-ID uniqueness, but deliberately does not require response or assertion `InResponseTo` to match an issued request ID. Implementations claiming compatibility must preserve that acceptance behavior while keeping signature, issuer, destination, assertion, CSRF, and replay checks intact. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlConfiguration.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlMessageIdChecker.java`]

At trace log level, the integration logs the full authenticated principal attribute map. Validation pages also expose all attributes to the authenticated system administrator. Deployments must treat diagnostic logs and validation output as identity data that may contain secrets or personal information. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlStatusChecker.java`; `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationAction.java`]

2. **Unsigned AuthnRequest.** Given valid required settings and request signing disabled with no service-provider key, when `/sessions/init/saml` is invoked, the response redirects to the configured login URL with nonblank `SAMLRequest` and `RelayState`, no `SigAlg` or `Signature`, issuer equal to application ID, destination equal to login URL, and ACS equal to the public callback. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/RedirectToUrlProvider.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

3. **Signed AuthnRequest.** Given request signing enabled and a valid PKCS#8 RSA private key plus X.509 service-provider certificate, when login initializes, the redirect contains `SAMLRequest`, `RelayState`, RSA-SHA256 `SigAlg`, and `Signature`. Missing either credential fails initiation rather than downgrading to unsigned. [Sources: `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`]

4. **Valid signed response.** Given valid RelayState, matching provider issuer, matching destination, a successful signed response verified by the configured certificate, valid assertion conditions, a new response ID, NameID, and mapped login/name attributes, when the callback is posted, the mapped identity is authenticated and the platform redirects to the requested page. [Sources: `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlIdentityProvider.java`]

5. **Assertion-signed response.** Given an unsigned response whose every assertion is individually signed by the configured asserting-party credential, when all response and assertion checks pass, authentication is accepted. If any assertion is unsigned while the response is unsigned, authentication fails. [Source: Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]

6. **Encrypted response.** Given a signed response with an encrypted assertion and a matching service-provider private key/certificate pair, when callback validation runs, the assertion is decrypted and mapped. Without a signed outer response or without usable decryption credentials, authentication fails and no plaintext fallback occurs. [Sources: `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; Spring Security 7.0.5 `BaseOpenSamlAuthenticationProvider`: https://github.com/spring-projects/spring-security/blob/7.0.5/saml2/saml2-service-provider/src/main/java/org/springframework/security/saml2/provider/service/authentication/BaseOpenSamlAuthenticationProvider.java]

7. **Wrong verification certificate.** Given a response signed by a key not represented by `sonar.auth.saml.certificate.secured`, when callback validation runs, signature verification fails and no identity is produced. Replacing the configured certificate with the correct X.509 value permits a new response to validate. [Source: `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

8. **Request-ID mismatch.** Given a cryptographically valid response whose `InResponseTo` does not correspond to a saved AuthnRequest, but with valid RelayState, new response ID, matching issuer and destination, and valid assertion, when callback validation runs, the `InResponseTo` mismatch alone does not cause failure. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeSaml2ResponseValidator.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlConfiguration.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlAuthenticator.java`]

9. **Replay.** Given one response ID successfully or unsuccessfully persisted by response validation, when another callback presents the same ID before expiry cleanup, it fails with error code `response_id_already_used`. Two concurrent first uses cannot both commit because the database message-ID index is unique. [Sources: `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlMessageIdCheckerIT.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`; `server/sonar-db-migration/src/main/java/org/sonar/server/platform/db/migration/version/v00/CreateInitialSchema.java`]

NameID is not used as a fallback. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/PrincipalToUserIdentityConverterTest.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

11. **Optional mapping behavior.** Given valid login and name, multiple email values, and group values containing duplicates and nulls, when mapping runs, the first email value is used only if nonnull, all nonnull groups are converted to strings and deduplicated, and only a nonempty group set requests group synchronization. Missing optional attributes do not fail login. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/PrincipalToUserIdentityConverter.java`; `server/sonar-auth-saml/src/test/java/org/sonar/auth/saml/PrincipalToUserIdentityConverterTest.java`]

12. **Issuer, destination, and audience boundaries.** Given an otherwise valid response, when response issuer differs from provider ID, a nonblank destination differs from callback URL, assertion issuer differs from provider ID, audience excludes application ID, or bearer recipient differs from callback URL, authentication fails. 13. **Administrator validation.** Given a logged-in system administrator, when `/saml/validation_init` completes an asserting-party round trip, the callback is transformed into a CSRF-protected POST to `/saml/validation`, the full SAML validation and replay checks run, no asserted user is registered, and an HTML report shows available and mapped attributes plus errors, warnings, signing configuration, and encryption observation. A nonadministrator or invalid token receives an authentication error instead of the report. [Sources: `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationInitAction.java`; `server/sonar-webserver-webapi/src/main/java/org/sonar/server/saml/ws/ValidationAction.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/SamlValidationRedirectionFilter.java`; `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SamlStatusChecker.java`]

Correcting the effective URL allows a later initialization to build a fresh registration. [Sources: `server/sonar-auth-saml/src/main/java/org/sonar/auth/saml/SonarqubeRelyingPartyRegistrationRepository.java`; `server/sonar-auth-saml/src/it/java/org/sonar/auth/saml/SamlIdentityProviderIT.java`]

A row expiring exactly at current time remains until a later run because deletion uses a strict earlier-than comparison.
