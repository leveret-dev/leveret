# LDAP Authentication Specification

## 1. Identity and license

This specification defines the LDAP authentication integration bundled in SonarQube Community Build 26.8.0.126808. The authoritative platform source is the `SonarSource/sonarqube` tag `26.8.0.126808` at commit `b33183b846cd47c7a811e280f5755f13d8fa8cc7`; the relevant product module is `server/sonar-auth-ldap`, with its login bridge in `server/sonar-webserver-auth`. The release was published on 2026-08-05. ## 2. Purpose, scope, and exclusions

The integration authenticates supplied credentials against one or more LDAP-compatible directories, including Active Directory when filters and attribute names are configured for that schema. It performs directory connection setup, optional TLS upgrade, bind authentication, user lookup, user-detail extraction, group lookup, referral handling, supported SASL mechanisms, and Kerberos V5 credential validation. It returns an authenticated external identity and the LDAP server key that accepted the credentials. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapUsersProvider.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`]

There is no separate Active Directory protocol implementation. Active Directory compatibility comes from configurable base DNs, filters such as those using `sAMAccountName`, attribute names, optional login lowercasing, LDAP referrals, and supported bind mechanisms. The integration does not discover a domain controller, read AD metadata, expand nested groups, process ranged attributes, write directory entries, change passwords, or perform periodic directory synchronization. [Sources: `sonar-application/src/main/assembly/conf/sonar.properties`; `sonar-core/src/main/java/org/sonar/core/config/CorePropertyDefinitions.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapUserMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapGroupMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`]

Local user creation and update, local group membership application, default-group behavior, sessions, cookies, tokens, authorization, permission checks, authentication-event storage, and HTTP error presentation belong to `platform/identity-access/` and `platform/http-api/`. This integration supplies protocol results to those owners and does not redefine them. [Source: `manifest/dependency-map.md`]

## 3. Dependencies and owned contracts

The integration depends on the JVM JNDI LDAP provider for LDAP connections, searching, LDAP bind mechanisms, referrals, LDAPS trust, and StartTLS; on JAAS and the JVM Kerberos V5 login module for GSSAPI credentials; on platform configuration for settings delivery; and on identity access for registration of the returned external identity. The default JNDI context factory is `com.sun.jndi.ldap.LdapCtxFactory`, and the Kerberos login module is `com.sun.security.auth.module.Krb5LoginModule`. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/Krb5LoginConfiguration.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`]

This specification owns these externally significant contracts:

- recognition of LDAP activation and single-server versus multi-server configuration;
- construction and testing of LDAP connections;
- ordered credential attempts and the server-key result;
- LDAP user and group searches and their mapping rules;
- supported simple, CRAM-MD5, DIGEST-MD5, and GSSAPI behavior;
- the external provider identifier `LDAP_<serverKey>` and the single-server key `LDAP_default`;
- failure classification at the LDAP boundary. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapRealm.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`]

## 4. Configuration surface and precedence

### 4.1 Activation and global settings

| Key | Default | Required behavior |
|---|---:|---|
| `sonar.security.realm` | unset | LDAP is active only when the value is exactly `LDAP`. Any other value leaves this integration inactive and it returns no authentication result. |
| `sonar.authenticator.downcase` | `false` | When true, lowercase the supplied login with locale-independent English rules before authentication, detail lookup, group lookup, provider-login output, and success-event reporting. Password is unchanged. |
| `sonar.authenticator.ignoreStartupFailure` | `false` | When false, a failed LDAP startup connection test prevents realm construction. When true, log the failure, retain active LDAP providers, and defer failure to later login attempts. |
| `ldap.servers` | unset or empty | An ordered string array of server keys. A nonempty value selects multi-server configuration; otherwise the unqualified single-server layout is used. |

[Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapRealm.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`; `sonar-core/src/main/java/org/sonar/core/config/CorePropertyDefinitions.java`; `server/sonar-process/src/main/java/org/sonar/process/ProcessProperties.java`; `server/sonar-auth-ldap/src/test/java/org/sonar/auth/ldap/LdapSettingsManagerTest.java`]

### 4.2 Per-server settings

For single-server mode, `<prefix>` is `ldap`. For multi-server mode it is `ldap.<serverKey>` for each key named by `ldap.servers`. Presence of `ldap.servers` is a layout switch, not a fallback chain: qualified settings are used and unqualified per-server settings are not inherited. The implementation explicitly rejects multi-server configurations that also contain `ldap.url` or `ldap.realm`; other unqualified LDAP values are not read by the qualified mappings. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`; `server/sonar-process/src/main/java/org/sonar/process/ProcessProperties.java`; `server/sonar-auth-ldap/src/test/java/org/sonar/auth/ldap/LdapSettingsManagerTest.java`]

| Key suffix | Default | Required behavior |
|---|---:|---|
| `.url` | none | Mandatory provider URL. `ldap://` and `ldaps://` are documented forms. An LDAPS server certificate must be trusted by the JVM trust store. |
| `.bindDn` | absent | Principal used for bind/search connections. Absence permits anonymous directory access for `simple`; every supported SASL mode requires a nonblank value during connection testing. |
| `.bindPassword` | absent | Credential paired with `.bindDn`; absence permits anonymous simple access. |
| `.authentication` | `simple` | Supported values are `simple`, `CRAM-MD5`, `DIGEST-MD5`, and `GSSAPI`. Matching of SASL values is case-sensitive. |
| `.realm` | absent | JNDI SASL realm used by non-GSSAPI context creation. It is not injected into the dedicated GSSAPI connection branch. |
| `.contextFactoryClass` | `com.sun.jndi.ldap.LdapCtxFactory` | JNDI initial-context implementation class. |
| `.StartTLS` | `false` | When true for a non-GSSAPI JNDI connection, establish LDAP, negotiate StartTLS before supplying authentication properties, then bind on the protected channel. |
| `.followReferrals` | `true` | Select JNDI referral mode `follow` when true and `ignore` when false. |
| `.saslQop` | absent | If present, pass through as `javax.security.sasl.qop` on ordinary JNDI contexts. |
| `.saslStrength` | absent | If present, pass through as `javax.security.sasl.strength`. |
| `.saslMaxbuf` | absent | If present, pass through as `javax.security.sasl.maxbuf`. |
| `.user.baseDn` | none | User-search root. The key must exist. A blank value suppresses that server's user mapping, so it cannot authenticate users. |
| `.user.request` | `(&(objectClass=inetOrgPerson)(uid={login}))` | User-search filter. The symbolic `{login}` placeholder is converted to a JNDI filter argument and receives the normalized supplied login. |
| `.user.realNameAttribute` | `cn` | First value becomes external display name. A missing attribute becomes an empty value and the login is used as the local registration name. |
| `.user.emailAttribute` | `mail` | First value becomes external email. A missing or blank value becomes no email in the registration result. |
| `.group.baseDn` | absent | Group-search root. Missing or blank disables group mapping for that server. If no server has group mapping, no LDAP group provider is installed. |
| `.group.request` | `(&(objectClass=groupOfUniqueNames)(uniqueMember={dn}))` | Group-search filter. Every brace-delimited placeholder names either `dn` or a user attribute needed from the user entry. |
| `.group.idAttribute` | `cn` | First value from each matching group entry becomes the external group identifier. |

[Sources: `sonar-application/src/main/assembly/conf/sonar.properties`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapUserMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapGroupMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapAuthenticatorIT.java`]

The three `.saslQop`, `.saslStrength`, and `.saslMaxbuf` keys are consumed by the LDAP module but are not listed in the shipped `sonar.properties` LDAP template or the process property registry. Values placed in the properties file are still visible to the module; environment-variable override discovery is guaranteed only for registered keys or keys already present in that file. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-main/src/main/java/org/sonar/application/config/AppSettingsLoaderImpl.java`; `server/sonar-process/src/main/java/org/sonar/process/ProcessProperties.java`]

Within this integration, `ldap.servers` has absolute precedence over the single-server layout, explicit values override the defaults above, and there is no per-login configuration override. Settings and constructed mappings are cached for the lifetime of the LDAP realm; changing connection or mapping settings requires realm reconstruction, normally a server restart. ## 5. Connection lifecycle

When LDAP is inactive, no context factories, user provider, group provider, or authenticator are constructed. When active, the realm builds a context factory for every configured server, builds user mappings in `ldap.servers` order, optionally builds group mappings, then opens one bind context per configured server as a startup test. The first startup failure stops further tests. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapRealm.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`]

An ordinary bind/search context receives authentication method, provider URL, context factory, referral mode, optional principal, optional credentials, optional SASL realm, and optional SASL quality properties. Bind/search contexts enable the JVM LDAP connection pool except when StartTLS is active. User-password contexts never enable pooling. Each password-validation context is closed after its attempt; search contexts are closed after the search is started. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/ContextHelper.java`]

With StartTLS, the initial connection deliberately carries no authentication principal or credential. The integration negotiates TLS, converts negotiation I/O failure into a naming failure, adds authentication properties only after negotiation, and explicitly reconnects to perform the bind. StartTLS connections are not pooled. The GSSAPI bind-context path is separate and does not perform this StartTLS sequence even if `.StartTLS` is true. [Source: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`]

With `ldaps://`, TLS is provided by JNDI from connection establishment. Certificate trust and hostname behavior are those of the pinned JVM LDAP provider and JVM trust store; this integration exposes no separate trust-store or hostname-verifier setting. [Sources: `sonar-application/src/main/assembly/conf/sonar.properties`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`]

No integration-specific connection timeout, read timeout, retry count, backoff, LDAP paging control, search time limit, or search count limit is configured. Directory and JVM defaults therefore bound those operations. [Source: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`]

## 6. Authentication processing

### 6.1 Ordered server selection

The input is a login and optional password supplied by the platform credential flow. Login lowercasing is applied first when enabled. The authenticator visits only servers with nonblank user mappings and preserves the order of `ldap.servers`; single-server mode uses the server key `default`. It stops at the first server that validates the credentials and returns that key. If every attempt fails, it returns an undifferentiated authentication failure. [Sources: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapAuthenticationResult.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapAuthenticatorIT.java`]

A server may therefore contain the same login as another. The first server whose credentials succeed wins; if an earlier server contains that login but its password bind fails, later servers are still attempted. The successful server key controls subsequent detail and group lookups and forms part of the external provider identifier, preventing two servers' mappings from being accidentally combined. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapUsersProvider.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapAuthenticatorIT.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapGroupsProviderIT.java`]

### 6.2 Simple authentication

For `simple`, the integration searches under the configured user base DN with subtree scope and the configured filter. JNDI filter-argument substitution supplies the login rather than direct text interpolation. Zero matches continues to the next server. Exactly one match supplies its full namespace DN as the authentication principal. More than one match is a non-unique naming failure and is treated as no usable user on that server. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapUserMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/LdapSearchIT.java`]

The integration rejects a null or empty password before an ordinary user bind. Otherwise it opens a nonpooled user context with the discovered DN and password. Successful context creation authenticates the user; any naming failure is a credential failure for that server and does not abort attempts against later servers. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapAuthenticatorIT.java`]

### 6.3 CRAM-MD5 and DIGEST-MD5

For the recognized SASL values `CRAM-MD5` and `DIGEST-MD5`, the supplied login itself is the principal; authentication does not first discover a DN. A nonblank `.bindDn` is required by startup testing. Password validation opens a nonpooled user context using the selected SASL mechanism and optional realm and quality properties. After success, user-detail lookup still performs the configured unique user search; successful credential validation without a unique mapped entry does not yield a platform identity. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapAuthenticatorIT.java`]

### 6.4 GSSAPI and Kerberos V5

For `GSSAPI`, both directory bind/search credentials and user credentials are validated through JAAS Kerberos V5. The integration installs a process-wide JAAS configuration containing one required `com.sun.security.auth.module.Krb5LoginModule`, supplies the configured or user principal and password through name and password callbacks, logs in, and performs the directory bind-context creation under the resulting subject. User authentication itself is a Kerberos login followed by logout; an authentication-login failure returns false, while a logout failure is only warned and does not reverse the successful result. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/Krb5LoginConfiguration.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/CallbackHandlerImpl.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`]

The JAAS configuration ignores application names, has no module options, and cannot be refreshed through this integration. Kerberos realm and KDC discovery therefore depend on JVM Kerberos configuration, including `java.security.krb5.conf` where used. A realm-qualified principal is accepted; an unqualified principal may use the JVM default realm. The LDAP `.realm` setting is not applied in the dedicated GSSAPI branch. Installing the JAAS configuration changes process-global security state, so the server process must not host an incompatible JAAS consumer. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/Krb5LoginConfiguration.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/KerberosIT.java`]

## 7. User-detail mapping

After password validation, the successful server's user search is repeated with subtree scope and must again return exactly one result. Only the configured name and email attributes are requested. The first value of each is treated as a string; a missing attribute becomes an empty string. Zero matches returns no details, while search or decoding failures become LDAP errors. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapUsersProvider.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapUserMapping.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapUsersProviderIT.java`]

The protocol output contains provider login equal to the normalized login, display name equal to the mapped name or the login when the name is empty, and email equal to the trimmed mapped email or absent when blank. The provider key and name are both `LDAP_<serverKey>`; the provider is enabled and allows first-login user registration. Display metadata is absent. Local identity collision handling and registration policy remain identity-access behavior. [Source: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`]

## 8. Group mapping

Group lookup occurs only when at least one nonblank group base DN caused a group provider to be installed. For the successful server, the integration first repeats the unique user search and requests every user attribute named by placeholders in that server's group filter. The reserved placeholder `{dn}` receives the user's full namespace DN; any other placeholder receives the first string value of that LDAP user attribute, or null if absent. The resulting values are supplied through JNDI filter arguments. A group request must contain at least one brace-delimited placeholder; a placeholder-free request is not a supported configuration. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapGroupMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`]

The integration searches the group base DN with subtree scope, requests only the configured group-ID attribute, reads the first string value from every match, and returns a deduplicated unordered set. This supports DN membership, POSIX-style user-attribute membership, and filters combining both styles. It does not recursively expand nested groups or impose ordering. An unknown user produces an empty group set. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapGroupsProviderIT.java`]

Whenever any server has enabled group mapping, the installed group provider causes every successful LDAP login to attach the returned set, including an empty set, and request identity-access group synchronization. If the successful server has no group mapping while another server does, its returned set is empty. Only when group mapping is globally absent is no group set attached and synchronization not requested. Identity access owns local group matching, default-group rules, and the effect of an empty synchronized set. [Sources: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`; `manifest/dependency-map.md`]

## 9. Referrals and partial results

`followReferrals=true` asks JNDI to follow referrals; `false` asks it to ignore them. When ignored-referral handling produces a `PartialResultException` while checking whether a search has more results, the integration treats that point as the end of available results and logs diagnostic detail rather than failing the unique-result check. Following referrals can cross directory trust boundaries and is enabled by default. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/LdapReferralsIT.java`]

## 10. State, concurrency, and persistence

The integration persists no LDAP credentials, directory objects, or synchronization cursor. Context factories and mappings are constructed once and shared. Each authentication, detail lookup, and group lookup uses operation-local JNDI contexts or the JVM bind connection pool. Returned collections are newly created per request. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`]

Concurrent GSSAPI operations share the process-wide JAAS configuration installed by this module. Directory connection pooling is delegated to the JVM and is enabled only for ordinary bind/search contexts without StartTLS. There is no module-owned lock, queue, retry state, or background synchronization lifecycle. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/Krb5LoginConfiguration.java`]

## 11. Failure, partial-result, and recovery behavior

- Missing or blank `.url` for any configured server is a configuration failure. Missing `.user.baseDn` is also a configuration failure; an explicitly blank user base suppresses that mapping. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapUserMapping.java`]
- A failed startup bind aborts realm startup by default. With `sonar.authenticator.ignoreStartupFailure=true`, startup continues with active providers; later requests retry the directory naturally because no negative connection state is cached. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapRealm.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/LdapRealmIT.java`]
- User-search naming failures, non-unique matches, password-bind failures, and bad Kerberos credentials are treated as failure for that server and permit later configured servers to be tried. If none succeeds, the platform receives an authentication failure without directory-specific detail. [Source: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`]
- After credential success, missing user details or any detail/group lookup exception aborts the overall login rather than returning a partial identity. Group lookup for a user absent from the directory returns an empty set; malformed or missing group-ID attributes fail group mapping. [Sources: `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapUsersProvider.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`]
- StartTLS negotiation failure is surfaced as a directory naming failure. Invalid context-factory classes, unsupported authentication mechanisms, trust failures, and protocol errors are delegated JVM failures and ultimately become startup or authentication errors according to the stage above. [Source: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`]
- Recovery consists of restoring directory reachability or credentials, correcting configuration, and reconstructing the realm when settings changed. There is no explicit reset API, circuit breaker, or scheduled retry. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapRealm.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`]

## 12. Security and trust boundaries

Directory URLs, bind credentials, search filters, context-factory class names, certificates trusted by the JVM, referral targets, and Kerberos configuration are administrator-controlled trusted configuration. A custom context factory executes inside the server process. Referrals may extend the network and credential trust boundary beyond the originally configured host. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `sonar-application/src/main/assembly/conf/sonar.properties`]

A simple bind over unprotected `ldap://` does not provide transport confidentiality. Deployments handling passwords must use trusted LDAPS or StartTLS as supported above. StartTLS protects credentials by negotiating before bind; GSSAPI uses its dedicated JAAS/JNDI path and does not use the StartTLS branch. [Source: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`]

Login and group placeholder values are passed as JNDI filter parameters instead of concatenated into filter text. The filter templates themselves remain trusted administrator input. Null and empty ordinary-bind passwords are rejected to prevent an accidental anonymous user bind from authenticating. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapUserMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapGroupMapping.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`]

Bind and user passwords are not included in the LDAP context debug representation. Provider URL, authentication mode, context factory, bind DN, realm, and referral mode may be logged; usernames, discovered DNs, and failure messages may also appear at diagnostic levels. Login sanitization removes carriage returns and line feeds from selected not-found messages, but directory-returned identity fields must still be treated as untrusted input by downstream code. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`]

## 13. Compatibility and limits

Compatibility requires LDAP search and bind behavior accepted by the configured JNDI provider. The shipped configuration supports `ldap://`, `ldaps://`, StartTLS, simple bind, CRAM-MD5, DIGEST-MD5, and GSSAPI. Search scope used by product user and group mappings is always subtree. Attribute values consumed for name, email, group placeholders, and group IDs must be representable as strings. [Sources: `sonar-application/src/main/assembly/conf/sonar.properties`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapUsersProvider.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapGroupsProvider.java`]

Only authentication-time reads are supported. There is no LDAP metadata endpoint, health endpoint, schema discovery, paged-results implementation, nested-group expansion, persistent directory cache, offline authentication, or directory write contract. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapModule.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`]

## 14. Acceptance scenarios

1. **Inactive realm.** Given complete LDAP settings but `sonar.security.realm` is absent or not exactly `LDAP`, when credentials are offered, the LDAP adapter returns no result and constructs no LDAP providers. Other platform authentication mechanisms remain eligible. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapRealm.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`]

2. **Simple bind success.** Given one reachable server, a unique user filter match, and a correct nonempty password, when login occurs, the integration binds as the discovered user DN, reloads name and email, and returns provider `LDAP_default`. Incorrect, empty, and null passwords do not authenticate. [Sources: `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapAuthenticatorIT.java`; `server/sonar-webserver-auth/src/test/java/org/sonar/server/authentication/LdapCredentialsAuthenticationTest.java`]

3. **Ordered multi-server fallback.** Given `ldap.servers=first,second`, the same login on both servers, a password valid only on `second`, and mappings for both, when login occurs, the first bind fails, the second succeeds, and detail and group lookup use only `second`; provider ID is `LDAP_second`. [Sources: `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapAuthenticatorIT.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapGroupsProviderIT.java`]

4. **Active Directory mapping.** Given an AD directory, a user filter using `sAMAccountName`, suitable base DNs and attributes, and `sonar.authenticator.downcase=true`, when a mixed-case login is supplied, the lowercase login is used consistently for search, authentication, external login, and group lookup. No AD-specific discovery is attempted. [Sources: `sonar-application/src/main/assembly/conf/sonar.properties`; `sonar-core/src/main/java/org/sonar/core/config/CorePropertyDefinitions.java`; `server/sonar-webserver-auth/src/test/java/org/sonar/server/authentication/LdapCredentialsAuthenticationTest.java`]

5. **StartTLS before credentials.** Given `.StartTLS=true` and a server supporting StartTLS, when a bind context is created, the initial connection contains no authentication credential, TLS is negotiated, and bind follows on the protected connection. If negotiation fails, authentication or startup fails and no clear-channel bind is attempted. [Source: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapContextFactory.java`]

6. **Startup failure policy.** Given an unreachable server and LDAP active, when the realm starts with the default policy, startup fails. With `sonar.authenticator.ignoreStartupFailure=true`, the realm remains active, records the ignored failure, and later login attempts fail or succeed according to current directory availability. [Sources: `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/LdapRealmIT.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapRealm.java`]

7. **Non-unique user.** Given a user filter returning two entries, when login occurs, the server is not accepted because a unique DN cannot be selected; later configured servers may still be attempted. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapAuthenticator.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/LdapSearchIT.java`]

8. **Group mapping styles.** Given one DN-based group and one POSIX-style group filter that references a user attribute, when the corresponding filter is configured and the user authenticates, every matching group ID is returned once. Unknown users return an empty set; nested membership is not expanded. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapGroupMapping.java`; `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/DefaultLdapGroupsProviderIT.java`]

9. **Optional attributes.** Given a valid user entry without the configured name or email attribute, when login succeeds, name falls back to the normalized login and email is absent. A missing user entry after credential success prevents registration rather than producing a partial identity. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/DefaultLdapUsersProvider.java`; `server/sonar-webserver-auth/src/main/java/org/sonar/server/authentication/LdapCredentialsAuthentication.java`]

10. **Kerberos authentication.** Given `GSSAPI`, valid bind credentials, a working JVM Kerberos configuration, and a valid user principal/password, when login occurs, JAAS validates the user and LDAP supplies mapped details and groups. A wrong password returns authentication failure; a wrong bind password prevents startup under the default policy. [Source: `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/KerberosIT.java`]

11. **Referral policy.** Given no explicit referral setting, when a context is built, referral mode is `follow`. Given `.followReferrals=false`, mode is `ignore`, and a partial-result exception during result-availability checking terminates the visible result set without turning that condition into a search failure. [Sources: `server/sonar-auth-ldap/src/it/java/org/sonar/auth/ldap/LdapReferralsIT.java`; `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSearch.java`]

12. **Invalid multi-server layout.** Given `ldap.servers` and an unqualified `ldap.url` or `ldap.realm`, when LDAP context factories initialize, configuration is rejected rather than mixing qualified and unqualified server state. [Sources: `server/sonar-auth-ldap/src/main/java/org/sonar/auth/ldap/LdapSettingsManager.java`; `server/sonar-auth-ldap/src/test/java/org/sonar/auth/ldap/LdapSettingsManagerTest.java`]
