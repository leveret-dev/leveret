## 2. Purpose, ownership, and exclusions

The analyzer recognizes Rust files, builds a tolerant concrete syntax tree, emits native syntax and complexity issues, obtains semantic lint diagnostics by running Clippy, imports external Clippy diagnostics, computes source measures, syntax highlighting and CPD tokens, and imports LCOV or Cobertura coverage. [Source: `sonar-rust-plugin/src/main/java/org/sonarsource/rust/plugin/RustPlugin.java`; `analyzer/src/analyze.rs`]

This component owns Rust-specific language recognition, analyzer rule repository `rust`, external repository `external_clippy`, Rust measures, issue locations, Cargo/Clippy integration and Rust coverage adapters. Platform plugin loading, rule activation storage, issue lifecycle, scanner report transport, metric aggregation, duplication matching and coverage persistence remain contracts of `platform/plugin-extension-runtime/`, `platform/project-configuration/`, `platform/analysis-results/`, `platform/scanner-gateway/` and `integrations/scanner-engine/`. [Source: project `manifest/dependency-map.md`]

Out of scope are Cargo, rustc, Clippy, Tree-sitter internals, dependency download behavior, build-script or procedural-macro behavior, and commercial rule extensions. No commercial capability is inferred from the public profile-contribution extension point. The release contains no native symbol index, semantic model exposed to other sensors, Rust test-result importer, custom-rule execution API, quick-fix producer or formatter. Coverage reports are imported, but tests are not run. [Source: `sonar-rust-plugin/src/main/java/org/sonarsource/rust/plugin/RustPlugin.java`; `sonar-rust-plugin/src/main/java/org/sonar/plugins/rust/api/RustRulesRepository.java`; `analyzer/src/analyze.rs`]

## 4. Native platform and process contract

The plugin packages one XZ-compressed native analyzer for each supported target. At sensor start it selects one target, decompresses that resource into scanner temporary storage, adds owner-execute permission when necessary, starts one subprocess, initializes all rule parameters once, analyzes Rust files sequentially through that process, and forcibly terminates the process when the sensor closes. The subprocess is not shared between analyses and stores no durable state. [Source: `sonar-rust-plugin/src/main/java/org/sonarsource/rust/plugin/PlatformDetection.java`; `AnalyzerFactory.java`; `Analyzer.java`]

| Runtime observation | Selected packaged binary | Compatibility detail |
|---|---|---|
| OS name contains `windows`; architecture contains `amd64` | `win-x64/analyzer.exe.xz` | Windows ARM and non-`amd64` architecture strings are unsupported. |
| OS name contains `linux`; architecture contains `amd64` | `linux-x64-musl/analyzer.xz` | Binary target is x86-64 musl. |
| OS name contains `linux`; architecture contains `aarch64` | `linux-aarch64-musl/analyzer.xz` | Binary target is AArch64 musl. |
| OS name contains `mac os`; architecture contains `aarch64` | `darwin-aarch64/analyzer.xz` | Apple Silicon. |
| OS name contains `mac os`; any other architecture string | `darwin-x86_64/analyzer.xz` | Detection deliberately falls back to Darwin x86-64 rather than verifying an x86 string. |
| Any other combination | None | Adds a unique analysis warning; aborts only when fail-fast is true. |

OS matching is case-insensitive; architecture substring matching is case-sensitive. The packaged native analyzer depends on `tree-sitter` `0.26.0` and `tree-sitter-rust` `0.24.0`. [Source: `sonar-rust-plugin/src/main/java/org/sonarsource/rust/plugin/PlatformDetection.java`; `AnalyzerFactory.java`; `analyzer/Cargo.toml`]

## 5. Language recognition and native analysis

### 5.1 Inputs and version handling

By default, every indexed `.rs` file receives language `rust`. A configured suffix list controls recognition. The native sensor requests every input file with that language and does not filter by MAIN versus TEST. Files are supplied as Unicode text; native transport uses UTF-8. There is no Cargo-project requirement for native parsing and no edition setting that changes the Tree-sitter grammar. Cargo edition is observed only for telemetry. Rust syntax support is therefore bounded by pinned Tree-sitter Rust grammar `0.24.0`, while compiler-backed lint support is bounded independently by installed Clippy. [Source: `plugin/RustLanguage.java`; `plugin/RustSensor.java`; `analyzer/src/tree.rs`; `plugin/Telemetry.java`]

Tree-sitter produces a recoverable tree even when syntax errors exist. Native outputs use 1-based lines and 0-based UTF-16 columns with end-exclusive ranges, converting Tree-sitter byte columns so supplementary Unicode characters occupy two UTF-16 units. [Source: `analyzer/src/tree.rs`; `analyzer/src/rules/parsing_error_check.rs`; `analyzer/src/analyze.rs`]

### 5.2 Processing stages

For each file, the native analyzer parses once, then derives highlighting, measures, CPD tokens and issues from the same tree. The host saves each output independently. Invalid host ranges for highlighting, CPD or issues are logged and skipped individually; other valid outputs remain. A file-content I/O failure is logged and that file contributes no native result. [Source: `analyzer/src/analyze.rs`; `plugin/RustSensor.java`]

### 5.3 Measures

The sensor emits these integer Core Metrics for each Rust input file:

| Metric key | Rust calculation |
|---|---|
| `ncloc` | Count of distinct source rows reached by leaf syntax nodes. |
| `comment_lines` | Count of distinct rows containing nonblank line or block comment content; rows containing only whitespace and ASCII punctuation within a comment do not count. |
| `functions` | Number of Tree-sitter `function_item` nodes, including methods and nested functions represented by that node kind. |
| `statements` | Count of expression statements, local `let` declarations and empty statements. |
| `classes` | Count of struct and enum declarations; unions, traits and implementations do not increment this measure. |
| `cognitive_complexity` | Sum of all Cognitive Complexity increments in the file. |
| `complexity` | Cyclomatic Complexity: one for each nonempty function body, closure, if, loop, while, for, logical binary operator, and match arm with a nonempty value. |

Cognitive Complexity increments for non-else-if conditionals, else clauses, while/loop/for/match constructs, labeled break/continue, each transition between logical AND and OR sequences, and nesting inside control structures, nested functions and closures. Else and logical-sequence increments do not receive nesting cost. Recursion is not detected. [Source: `analyzer/src/visitors/metrics.rs`; `cognitive_complexity.rs`; `cyclomatic_complexity.rs`; `plugin/RustSensor.java`]

### 5.4 Highlighting

Highlighting uses the pinned Tree-sitter Rust highlight query. Captures saved to the scanner are `KEYWORD`, `STRING`, `CONSTANT` and `COMMENT`. Boolean, integer and floating literals are constants. Documentation and ordinary comments are distinguished during query processing but both are emitted as `COMMENT`; documentation captures are prevented from being emitted twice as ordinary comments. Unrecognized query capture classes are ignored. [Source: `analyzer/src/visitors/highlight.rs`]

### 5.5 CPD

CPD visits leaf nodes and preserves source spelling except that integer and floating literals become `NUMBER`, string content and whole raw-string literals become `STRING`, and missing/error nodes are omitted. Empty source roots are omitted. A `cfg(test)` attribute with the exact simple `test` argument marks its next named sibling as excluded. Exclusion state holds only one node identifier: a nested, also-recognized `cfg(test)` attribute overwrites the outer identifier, and exiting the nested target clears all exclusion state, so later leaf nodes in the outer test subtree resume producing CPD tokens. Without such a nested recognized attribute, the entire marked sibling is excluded. Nested expressions such as negated test configuration are not recognized at all. Other test files and test attributes are not specially excluded. Token ranges use the common UTF-16 coordinate conversion. Duplicate-block detection and thresholds belong to the platform. [Source: `analyzer/src/visitors/cpd.rs`; `plugin/RustSensor.java`]

No symbol, reference or semantic-index output is emitted. [Source: `analyzer/src/analyze.rs`; `plugin/RustPlugin.java`]

## 6. Cargo discovery and Clippy

### 6.1 Cargo manifests

Manifest discovery first evaluates `sonar.rust.cargo.manifestPaths` entries. A concrete existing file is accepted regardless of its filename; otherwise the entry is expanded as a pattern. If this produces at least one file, those files are the complete result and root discovery is not added. If it produces none, the analyzer uses `<analysis-base>/Cargo.toml` when that path exists. No recursive default search is performed. Duplicate matches are retained. [Source: `sonar-rust-plugin/src/main/java/org/sonarsource/rust/cargo/CargoManifestProvider.java`]

Native analysis does not require a manifest. Clippy execution requires at least one; absent manifests produce an analysis warning and optional fail-fast abort. Each discovered manifest is processed sequentially with its parent directory as the Cargo working directory. [Source: `plugin/RustSensor.java`; `clippy/ClippySensor.java`]

### 6.2 Analyzer-managed Clippy execution

Execution is enabled by default. Before any manifest is linted, the analyzer runs `cargo --version` and `cargo clippy --version` from analysis base and requires a nonblank first output line from each. It enforces no numeric minimum or maximum version. Failure warns, skips all managed Clippy work and aborts only under fail-fast. [Source: `clippy/ClippyPrerequisite.java`; `ClippySensor.java`]

For each manifest, the analyzer runs Cargo Clippy quietly with JSON messages. Offline mode adds Cargo's `--offline`. After Cargo arguments, it disables the `clippy::all` group and enables each Clippy lint mapped from an active rule in repository `rust` as a warning. Native-only rules are not mapped. This warning level is intended to keep lint findings from producing a nonzero process status. A nonzero status, launch failure or interruption fails the managed Clippy phase; interruption restores thread interruption. There is no retry or process timeout. [Source: `clippy/ClippyRunner.java`; `ClippySensor.java`; `plugin/RustRulesDefinition.java`]

Only JSON lines whose first character is an opening brace are parsed. A record is retained only when manifest path, message, code and code text exist and code text begins with `clippy`. Analyzer-managed findings are saved under the mapped `rust:S…` rule, use the plugin's stable mapped message rather than Clippy's version-specific text, and use only the first diagnostic span. Findings with unknown mappings, missing indexed files or invalid locations are skipped individually. [Source: `clippy/ClippyUtils.java`; `ClippySensor.java`]

### 6.3 External Clippy report import

Presence of `sonar.rust.clippyReport.reportPaths` activates import independently of managed execution. Input is Cargo's newline-delimited JSON message stream, normally produced with `cargo clippy --message-format=json`; it is not a JSON array. Each report is parsed independently. One malformed JSON line invalidates that report, but other report files continue. Non-JSON-prefixed lines and non-Clippy diagnostics are ignored. [Source: `clippy/ClippyReportSensor.java`; `ClippyUtils.java`]

A retained external diagnostic must use a cataloged `clippy::<rule-id>` code and contain at least one span. The external issue uses engine `clippy`, rule ID without the prefix, original Clippy message, `CODE_SMELL`, `MAJOR` severity and five-minute constant remediation effort. Only the first span is used. Clippy's 1-based columns are converted to 0-based scanner columns. [Source: `clippy/ClippyReportSensor.java`; `ClippyUtils.java`; analyzer-commons `ExternalRuleLoader.java` from exact source artifact `sonar-analyzer-commons:2.28.0.5085`]

An absolute span path is tried directly. For a relative span path, a relative manifest path is first resolved against analysis base; a value ending in `Cargo.toml` contributes its parent directory, while any other value is treated as the directory itself. If that directory lies inside analysis base, candidates are tried from it and then every ancestor through analysis base; if outside, the raw span path and manifest-relative path are tried. The first indexed path wins. Missing files produce one deduplicated analysis warning category. Unknown rule IDs are logged but deliberately produce no analysis warning. Missing spans, invalid paths and invalid ranges produce a generic deduplicated warning, and later diagnostics continue. [Source: `clippy/ClippyUtils.java`; `ClippyReportSensor.java`; corresponding tests]

## 8. Coverage import

### 8.1 Common path and file behavior

LCOV and Cobertura sensors run only when their respective property key is present and at least one Rust file exists. Report entries may be concrete files or patterns, relative to analysis base or absolute. Only indexed MAIN Rust files are candidates for coverage. Resolution first asks the scanner for the report path exactly; if absent, a sanitized suffix lookup is used. Ambiguous suffixes select the first indexed leaf, so unique source suffixes are required for deterministic mapping. Missing reports or unmatched source files are nonfatal. [Source: `coverage/LcovSensor.java`; `CoberturaSensor.java`; `common/ReportProvider.java`; `common/FileLocator.java`]

Coverage output records line hits and, per line, total and covered conditions. Line numbers must be within `1..inputFile.lines`. Coverage is saved separately for each parsed file/report result; the Rust plugin performs no cross-report deduplication. Platform coverage handling owns any later combination. [Source: `coverage/CodeCoverage.java`; `CoverageUtils.java`]

### 8.2 LCOV

LCOV recognizes `SF:`, `DA:` and `BRDA:` records; unrelated records are ignored. An `SF:` opens or replaces current file coverage. A duplicate source file in one report is recorded as a problem and the later record replaces the earlier object. `DA:` accepts line and execution count, ignoring optional later fields; repeated line entries sum. `BRDA:` accepts line, block, branch and taken count. Branch identity is the direct concatenation of block and branch text without a separator; colliding concatenations merge. Negative taken counts become zero; a nonnumeric value, including LCOV's dash marker, is a problem. Branch records sum by identity. [Source: `coverage/LcovParser.java`; `CodeCoverage.java`]

Syntax, number, unknown-file and out-of-range problems are collected with report line numbers and do not invalidate other valid LCOV records. Failure to read or otherwise parse one report skips that report while others continue. When saved, conditions are the number of distinct branch identities; covered conditions have summed taken count greater than zero. For a branch line, emitted line hits equal imported line hits plus covered-condition count. [Source: `coverage/LcovParser.java`; `CoverageUtils.java`; `LcovSensor.java`]

### 8.3 Cobertura

Cobertura parses XML and examines every `class` element. Each class needs `filename`; missing or unresolved filenames are recorded as location-aware problems. Only direct `lines` children of a class are consumed. A `line` needs integer `number` and `hits`; missing or malformed attributes skip that line with a problem. Repeated lines sum hits. Branch handling occurs only when `branch` is exactly `true`; `condition-coverage` must match a percentage followed by covered/total integer counts, with covered not greater than total. It creates `total` branch identities numbered from zero and marks the first `covered` identities as taken. [Source: `coverage/CoberturaParser.java`; `CodeCoverage.java`]

A later class resolving to the same file replaces the earlier class coverage without a problem. XML/read failures and unchecked line-range failures skip the entire report through the sensor's report-level catch; other reports continue. Saving one file failure does not prevent later files. [Source: `coverage/CoberturaParser.java`; `CoberturaSensor.java`]

## 9. Failure, partial results, and recovery

- Unsupported native platform, native binary extraction/start failure, missing Cargo manifests, Clippy prerequisite failure and Clippy execution failure add analysis warnings as described. Only these paths consult `sonar.internal.analysis.rust.failFast`; when enabled they throw an analysis failure. [Source: `plugin/RustSensor.java`; `clippy/ClippySensor.java`]
- Native file-content I/O failure, invalid emitted location and coverage parse/save errors are logged but do not consult fail-fast. Valid files or records continue where their enclosing sensor catch permits. [Source: `plugin/RustSensor.java`; coverage sensors]
- Native parser syntax errors ordinarily produce `S2260` while measures, highlighting and stable CPD tokens still emit from the recovered tree. [Source: `analyzer/src/rules/parsing_error_check.rs`; `analyzer/src/visitors/cpd.rs`]
- A native global error, including highlight-query construction failure or invalid/missing `S3776:threshold`, logs to native standard error and terminates the subprocess. Host I/O failure then causes the current file to be skipped; there is no subprocess restart, so later requests to that process may also fail. [Source: `analyzer/src/main.rs`; `rules/rule.rs`; `visitors/highlight.rs`; `plugin/Analyzer.java`; `RustSensor.java`]
- Compatibility caveat: if native analysis returns a file-scoped internal error before producing output, the subprocess writes a warning and resumes its command loop without emitting a result terminator for that request. The host has no read timeout, so that path can block rather than recover. [Source: `analyzer/src/main.rs`; `plugin/Analyzer.java`]
- Missing external Clippy reports, invalid reports, unknown files and invalid diagnostics use deduplicated analysis warnings. Unknown external rule IDs are silent at warning level. Successfully parsed reports and later diagnostics remain usable. [Source: `clippy/ClippyReportSensor.java`]
- There are no analyzer-managed retries, checkpoints or persistent recovery state. Rerunning analysis is recovery after correcting environment, settings, report data or source. [Source: all sensor implementations]

## 10. Lifecycle, concurrency, security, and trust

Native file analysis and per-manifest Clippy invocations are sequential. Clippy stdout and stderr are drained on daemon worker threads to avoid child-process pipe blockage; after process exit the stream drain waits at most five minutes. The native process uses direct binary streams and is forcibly destroyed at sensor close. Report parsing and issue creation are sequential. No analyzer-owned data persists beyond scanner outputs, telemetry and temporary files. [Source: `common/ProcessWrapper.java`; `StreamConsumer.java`; `plugin/Analyzer.java`; `RustSensor.java`; `clippy/ClippyRunner.java`]

Managed Clippy crosses a major trust boundary: it invokes the locally resolved `cargo` executable in project-controlled directories and may compile dependencies, execute build scripts or procedural macros, and access the network unless offline mode is enabled. The analyzer does not sandbox Cargo or verify executable identity. Analyze only trusted projects and toolchains; use offline mode only after required dependencies are locally available. [Source: `clippy/ClippyRunner.java`; `ClippySensor.java`]

The bundled native executable is trusted plugin content, decompressed and executed from scanner temporary storage. The analyzer does not authenticate that resource separately at runtime. Manifest and report settings may name files outside analysis base; report contents, paths, spans and line numbers are untrusted and validated only by the described parsers and scanner range APIs. LCOV files and Cargo manifests are read wholly as line collections, Cobertura XML wholly as text/DOM, and Rust source wholly as a string/UTF-8 byte array. No explicit analyzer-level size limit exists beyond JVM/native collection and 32-bit transport lengths. [Source: `plugin/AnalyzerFactory.java`; `Analyzer.java`; `common/ReportProvider.java`; `coverage/LcovParser.java`; `CoberturaSensor.java`; `plugin/Telemetry.java`]

Telemetry fields emitted by this analyzer are `rust.language.edition`, `rust.clippy.version`, `rust.coverage.format`, `rust.clippy.usage`, `rust.dependencies.count` and `rust.dependencies`. Manifest dependency telemetry is best-effort over direct normal, development, build, workspace and target-specific dependency tables; it deduplicates name/version tokens. The joined dependency value is limited to 1,000 characters; oversized sets are randomly sampled at token boundaries and end with `,...`, so the sampled list is nondeterministic while count remains complete for successfully read manifests. Manifest read failures do not fail analysis. Platform telemetry policy and upload gating remain outside this analyzer. [Source: `plugin/Telemetry.java`; project `manifest/dependency-map.md`]

## 11. Compatibility and limits

- Java plugin bytecode targets Java 17 and declares Sonar plugin API `13.8.0.4399`; release build uses analyzer-commons `2.28.0.5085`, XML parsing from that release, Gson `2.14.0` and XZ `1.12`. [Source: `sonar-rust-plugin/build.gradle.kts`]
- Native syntax recognition is grammar-based, not compiler-semantic. Conditional compilation, macro expansion, Cargo feature resolution and type inference do not alter native metrics/rules. Clippy findings may reflect all of those through the installed toolchain. [Source: native analyzer sources; Clippy sensors]
- No supported Rust edition list is hard-coded. No Clippy version range is enforced. External rule metadata is fixed to Rust/Clippy `1.97.1`; a different installed Clippy may omit cataloged lints or emit newer unknown lints. Unknown external lints are ignored, and managed execution can request active lints unsupported by an older Clippy, causing command failure. [Source: `clippy/ClippyPrerequisite.java`; Clippy metadata `upstream.json`; `ClippyReportSensor.java`; `ClippyRunner.java`]
- Native analysis accepts all indexed Rust files, including TEST files. Coverage accepts MAIN Rust files only. CPD's special test exclusion is limited to the exact simple `cfg(test)` sibling pattern. [Source: `plugin/RustSensor.java`; coverage sensors; `analyzer/src/visitors/cpd.rs`]
- No explicit source, report, diagnostic, token, issue, branch or manifest-count ceiling is imposed. Memory, scanner APIs, child processes and 32-bit native message lengths are practical bounds. [Source: `plugin/Analyzer.java`; parsers and sensors]

## 12. Acceptance scenarios

1. **Default recognition and native output.** Given indexed source ending in `.rs` on a supported platform, with no suffix override, analysis classifies it as Rust, emits all seven file measures, available highlighting and CPD tokens, and native issues with UTF-16 ranges. A source file with another suffix is not Rust unless configured.
2. **Suffix replacement.** Given `sonar.rust.file.suffixes` containing a custom suffix and not `.rs`, a custom-suffix file is analyzed as Rust and an `.rs` file is not selected through the Rust language suffix contract.
3. **Platform matrix.** Given Linux with architecture text containing `aarch64`, the AArch64 musl resource is extracted and run. Given unsupported OS/architecture, native analysis emits one analysis warning; analysis continues by default and fails when internal fail-fast is true.
4. **Recoverable syntax.** Given malformed Rust that Tree-sitter represents with error or missing nodes, `S2260` locations follow error-node or previous-sibling/parent recovery rules while other derivable native outputs remain available.
5. **Complexity threshold.** Given an outer function whose Cognitive Complexity is 16 and threshold is 15, one `S3776` issue is placed on its name with increment secondary locations. At complexity 15, no issue is emitted. Invalid threshold text terminates native analysis as a global error.
6. **Cargo precedence.** Given an explicit manifest pattern resolving at least one file plus a root `Cargo.toml`, only explicit results are used. Given explicit entries resolving none, root manifest is used. Given neither, native analysis still runs but managed Clippy warns and skips.
7. **Managed Clippy activation.** Given managed Clippy enabled, prerequisites available and only `rust:S6164` active among mapped rules, command construction disables `clippy::all` then warning-enables `clippy::approx_constant`; a retained diagnostic becomes a `rust:S6164` issue using stable mapped message and first span.
8. **Offline Clippy.** Given offline true, managed Clippy receives Cargo offline mode. Missing cached dependencies may make Cargo nonzero; analyzer warns and continues by default or fails under fail-fast.
9. **External Clippy partial import.** Given two report files where one is malformed and one contains a cataloged diagnostic with a resolvable first span, the malformed report produces the invalid-report warning and the valid diagnostic becomes `external_clippy:<rule-id>` with original message. Unknown rule diagnostics create no issue and no analysis warning.
10. **External path resolution.** Given a workspace manifest under analysis base and a relative span path, resolution tries the crate directory then ancestors through base and attaches to the first indexed match. Given no match, the issue is skipped and unknown-file warning is deduplicated.
11. **LCOV partial data.** Given valid `SF`, `DA` and `BRDA` records plus one malformed record, valid coverage is saved and the malformed record appears only as a debug-level detailed problem after a summary warning log. A source path that maps only to a TEST Rust file is not imported.
12. **Cobertura conditions.** Given a class resolving to a MAIN Rust file and a branch line reporting two covered of three total conditions, output records three conditions, two covered, and line hits according to imported hits plus two covered conditions. Invalid covered-greater-than-total data is skipped as a problem.
13. **CPD test exclusion.** Given an exact simple test configuration attribute followed by a named item containing no nested recognized test configuration, the full item produces no CPD tokens. Given another exact simple test configuration inside that item, leaves through the nested target remain excluded, but leaves after the nested target within the outer item produce tokens because the single exclusion slot was cleared. A negated test configuration does not trigger exclusion.
14. **Dual coverage configuration.** Given both coverage path settings, both sensors parse their reports independently and attempt coverage saves. The analyzer does not deduplicate cross-format observations; platform coverage semantics determine final combination.
15. **Trust boundary.** Given managed Clippy enabled for a project containing executable build logic, analysis may execute that logic through Cargo. Disabling managed Clippy prevents that invocation; external report import remains available if configured.
