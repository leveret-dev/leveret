# TypeScript Analyzer Specification

## Identity, license, and authority

This specification covers TypeScript repository key `typescript`, language key `ts`, from bundled artifact `org.sonarsource.javascript:sonar-javascript-plugin:13.4.0.43982:multi`. Community Build `26.8.0.126808` pins this artifact. Source authority is SonarSource/SonarJS tag `13.4.0.43982`, commit `d02b514f8007f18a798876fc9361b9c233ab2f02`. Analyzer-owned source uses Sonar Source-Available License v1.0 (`LicenseRef-SSAL-1.0`); dependency notices remain separate. [I1][I2]

## Purpose, scope, dependencies, and ownership

The analyzer recognizes TypeScript and TSX variants, creates TypeScript programs where possible, applies active TypeScript rules with semantic/type information, emits issues and quick fixes, and produces same file artifacts and coverage/import behavior as JavaScript for TypeScript-owned files. JavaScript owns shared bridge/runtime contract at `../javascript/specification.md#shared-bridge-and-runtime-contract`; this file depends on that contract without redefining process selection, transport, lease, cache envelope, or Node lifecycle. CSS and embedded-host projection are out of scope here. Platform owns profiles, measure keys, issue lifecycle, persistence, and scanner report protocol. [B1][B2][T1]

## Inputs and language recognition

Language key is `ts`. `sonar.typescript.file.suffixes` defaults to `.ts,.tsx,.cts,.mts`. Configured suffixes are trimmed, lower-cased, dot-prefixed when needed, de-duplicated, and replace defaults. A `.vue` file belongs to JavaScript scanner language by default, but a script tag with `lang=ts` selects TypeScript parsing and TypeScript-compatible rule filtering for that file; Vue host-file ownership remains JavaScript. [B2]

Shared exclusions, max-size, minification, bundle detection, generated-source detection, source/test classification, environments, and globals follow JavaScript specification. Important precedence: presence of either `sonar.javascript.exclusions` or `sonar.typescript.exclusions` discards default exclusions and concatenates both configured arrays. `.d.ts` is excluded by default but becomes eligible if operator replaces defaults without retaining that pattern. [B2]

## TSConfig discovery, type information, and version behavior

`sonar.typescript.tsconfigPaths` is canonical; deprecated alias `sonar.typescript.tsconfigPath` is used only when canonical key is absent. Values accept exact paths and case-insensitive wildcard patterns. If at least one configured path resolves, that ordered set takes precedence over automatically discovered `tsconfig.json` files. If configured patterns resolve none, analyzer logs error and can use discovered configs. Automatic configs sort alphabetically; configured matches preserve property order. Project references discovered from a program are appended to same mode after missing references are warned and skipped. [T1][B2]

Each config is parsed with bundled TypeScript 6.0.3 and filesystem policy. An invalid config produces a warning naming highest supported TypeScript and does not prevent other configs. Missing extended config warns and requests dependency installation; project completes with partial semantics. Files in a program are analyzed once, using first processed program that contains them. [T1]

`sonar.javascript.disableTypeChecking=false` by default. When true, no project programs are created and every file is analyzed syntax-only. `sonar.javascript.createTSProgramForOrphanFiles=true` by default. With it enabled, accepted files not in any config are grouped by effective ECMAScript library and receive fallback programs; when false, they proceed without type information. Type-dependent rules are sanitized to no-op when parser services are unavailable. [T1][R2]

Effective standard library precedence is valid `sonar.javascript.ecmaScriptVersion`, then higher year derived from tsconfig `target` and nearest package Node signal (`@types/node`, `engines.node`, or related recognized metadata), then `esnext`; DOM is included. Orphan groups with same effective library share program. If earlier configs exist, merged non-library compiler options form fallback baseline while library remains package-specific. [T1]

SonarQube creates standard programs per config, discovers references, analyzes pending members, builds fallback programs, then clears program/source caches. SonarLint selects closest containing config for request, uses cached incremental builder programs, and invalidates caches when config, base directory, filesystem capability, discovery settings, or watched config changes. [T1]

## Processing, outputs, metrics, symbols, highlighting, and CPD

TypeScript parsing uses `@typescript-eslint/parser` backed by TypeScript 6.0.3. TSX/JSX mode follows program compiler option when known. Vue TypeScript parsing retries once with opposite JSX setting after ambiguity failure, then reports original error. Active rule eligibility is intersection of `typescript` compatibility, main/test scope, profile activation, dependency, ECMAScript/module, generated-source, and type-service gates. [B2][R2]

Main TypeScript files emit native issues, quick fixes, `functions`, `statements`, `classes`, cyclomatic and cognitive complexity, `ncloc`, `comment_lines`, per-line NCLOC and executable-line data, syntax highlighting, symbols, and CPD. Test files emit scope-eligible issues, highlights, symbols, and NOSONAR handling, but no persisted server structural measures or CPD. Highlight and CPD token semantics are identical to JavaScript contract: imports and supported `require` declarations are omitted from CPD, non-JSX string literals normalize to one image, and symbol locations exclude trailing type annotations. [M1][B2]

Parser failure is file-local, records analysis error, and emits `typescript:S2260` only when active. Rule output can include primary/secondary locations, effort gap, and quick fixes listed in catalog. Same runtime partial-result rules as JavaScript apply. [B2]

## Coverage and external reports

LCOV import is shared across `js` and `ts`: `sonar.javascript.lcov.reportPaths` and alias `sonar.typescript.lcov.reportPaths` are merged as a set, resolve absolute/relative/wildcard report files, and save only main JavaScript/TypeScript coverage. `SF`, `DA`, and `BRDA` records merge; missing reports yield no coverage; malformed records and unresolved sources warn without discarding valid records. [L1]

`sonar.eslint.reportPaths` accepts ESLint JSON for TypeScript files through shared importer. Null-rule parse messages are skipped, missing inputs warn, start-only/zero-length ranges expand to whole line, and exact native duplicates are removed by ESLint key, normalized path, and range. External engine is `eslint_repo`; packaged catalogs include `@typescript-eslint` among 1,177 accepted ESLint identifiers. [X1]

`sonar.typescript.tslint.reportPaths` imports TSLint JSON only in SonarQube. Each entry uses `name`, `ruleName`, `failure`, and zero-based start/end positions; line becomes one-based, equal start/end expands to whole line, and output uses external engine `tslint_repo`; 144 TSLint and 71 TSLint SonarTS packaged identifiers share that repository. Imported severity is Major and remediation effort is 5 minutes; rule type comes from packaged metadata. Missing report/input and unreadable JSON are logged; unaffected reports continue. [X1]

## Failure, recovery, security, and limits

Shared Node/bridge failures follow JavaScript contract. Invalid/missing tsconfig produces partial semantics rather than project failure unless runtime itself fails. Missing type information must never be replaced with guessed types; type-dependent rules remain silent. Per-file parser/runtime error does not invalidate other files unless fail-fast is enabled. Cancellation ends stream. [B1][B2][T1]

TSConfig files, `extends`, project references, package manifests, module paths, external reports, and source text are untrusted. Paths must be normalized within indexed/project policy, compiler resolution must honor filesystem capability and node-module lookup boundary, report locations must be range-checked, and project scripts must not execute during discovery. Explicit external Node and bridge settings remain operator trust decisions governed by shared contract. [B1][T1][X1]

Compatibility requires Java 17, plugin API minimum `9.14.0.375`, Node runtime described by shared contract, TypeScript 6.0.3, `@typescript-eslint` 8.65.0, and `vue-eslint-parser` 10.4.1. Compiler syntax/config newer than bundled TypeScript is unsupported and should surface a parse/config warning rather than silent reinterpretation. [I1][T1]

## Acceptance scenarios

1. With defaults, `.ts`, `.tsx`, `.cts`, and `.mts` are TypeScript; unrelated suffixes are not.
2. Canonical `sonar.typescript.tsconfigPaths` and alias both set: canonical values win.
3. Two configured configs resolve: their declared property order controls processing, and a file is analyzed once by first containing program.
4. One config is invalid and another valid: warning names invalid config; valid program and orphan fallback still run.
5. A config extends missing dependency: warning is emitted, partial program proceeds, and project metadata carries missing-config warning.
6. `disableTypeChecking=true`: all files get syntax analysis, type-dependent rules yield no issues, and syntax-only rules still execute.
7. Orphan program creation disabled: orphan TypeScript file is analyzed without type information rather than silently dropped.
8. An explicit valid ECMAScript override wins over tsconfig target and package Node signals.
9. TSLint zero-length location becomes whole-line external issue; unknown input path is skipped with warning.
10. Parser failure emits analysis error and optional `typescript:S2260`, without metrics or ordinary rule findings for that file.
