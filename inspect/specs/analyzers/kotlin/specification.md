## 2. Purpose, scope, and exclusions

Analyzer recognizes Kotlin/JVM source and two Kotlin Gradle DSL filenames, builds compiler-backed syntax and semantic models, executes native Kotlin and Gradle rules, emits source measures, line data, duplication tokens, and syntax highlighting, imports JVM test results, and imports Detekt, ktLint, and Android Lint findings.

Analyzer owns only Kotlin-specific recognition and observations. It does not own quality-profile persistence, active-rule precedence, issue lifecycle, scanner report transport, compute-engine persistence, or result APIs. Those contracts belong to `platform/project-configuration/`, `platform/plugin-extension-runtime/`, `integrations/scanner-engine/`, `platform/scanner-gateway/`, `platform/compute-engine/`, and `platform/analysis-results/`.

Excluded behavior:

- Kotlin/JS and Kotlin/Native semantic environments are not supported; compiler environment is JVM-only.
- General `.kts` scripts other than exact `build.gradle.kts` and `settings.gradle.kts` are not processed by native sensors.
- Test-source `.kt` files are not processed by main native rule/metric sensor because it selects `MAIN` files only.
- Analyzer defines no symbol-index output.
- Analyzer contains no coverage-report parser. Kotlin coverage is supplied by bundled JaCoCo integration described by `integrations/jacoco/`; this analyzer supplies source identity and executable-line data but does not own JaCoCo XML semantics.
- Commercial rule extensions are not described. Community plugin's own extension-provider callback registers nothing.
- Detekt, ktLint, and Android Lint engines are not executed. Only their reports and shipped compatibility metadata are imported.

## 4. Recognition and accepted inputs

### 4.1 Kotlin files

Language suffix matching uses configured `sonar.kotlin.file.suffixes`. If resolved array is empty, analyzer restores `.kt,.kts`. Main sensor then selects only files classified as language `kotlin`, type `MAIN`, and whose extension is not exactly `kts`. Consequently default native Kotlin analysis covers main `.kt` files. A custom non-`kts` suffix classified as Kotlin is accepted and parsed as Kotlin source.

Main sensor does not select test files or any `.kts` file. Source byte content is read through scanner filesystem. Whitespace-only files are loaded into compiler session but do not run visitors.

### 4.2 Kotlin Gradle DSL

Gradle sensor selects indexed files whose filename is exactly `build.gradle.kts` or `settings.gradle.kts`. It runs Gradle rule set only and supplies an empty library classpath. Selection is filename-based; arbitrary Kotlin scripts are excluded.

Project-level Gradle checks run only when `sonar.kotlin.gradleProjectRoot` is present and denotes same filesystem location as scanner module base directory. `S6631` checks for either Groovy or Kotlin settings file. `S6474` checks root `gradle/verification-metadata.xml`.

### 4.3 Compiler and semantic inputs

Each sensor creates one JVM compiler environment and one standalone K2 Analysis API session. All selected files are presented together as one source module named `module`, with a library module formed from valid classpath entries and a JDK module rooted at current Java home. Classpath order is Java binaries first, then Java libraries. Existing directories are accepted. Regular files are accepted only when their first bytes identify a ZIP/JAR; other entries are ignored.

Compiler configuration uses JVM target 1.8 for source analysis. `sonar.kotlin.source.version` is resolved through embedded compiler's recognized language-version table. Unknown nonblank values produce warning and fall back to `2.4`; absent or blank values also select `2.4`. Compiler API version follows selected language version.

Parser obtains Kotlin PSI and document mapping from K2 session, then rejects file when any PSI syntax-error element exists. Semantic rules use K2 call resolution, use-site types, symbols, overriding relationships, nullability, receiver types, and constant-value prediction where their individual detection requires it. Missing or incomplete classpath can therefore reduce semantic detections without preventing syntax-only rules.

## 5. Processing lifecycle, state, and concurrency

1. Sensor resolves active native checks and initializes each with its rule key and configured parameters.
2. File selection applies language/type/script and incremental rules.
3. Analyzer eagerly reads all selected files and creates shared compiler session so cross-file semantic resolution is available before file visitors run.
4. For each nonblank successfully parsed Kotlin file, visitors run in order: suppression discovery, metrics/line data, active checks, CPD tokenization, then highlighting. SonarLint omits CPD and highlighting.
5. Gradle sensor independently parses exact Gradle filenames and runs only Gradle checks; it emits no Kotlin metrics, CPD, or highlighting.
6. Compiler environment is disposed after sensor completion and global ZIP file-handle cache is cleared. This is required for Windows dependency replacement compatibility.
7. Surefire and external-report sensors process configured reports in their own sensor executions.
8. Project sensor publishes telemetry after module-level work when runtime API is at least 10.9.

Scanner framework serializes analyses. Compiler cleanup clears a global archive-handle cache and is not safe to overlap with another compiler analysis that still uses those handles. No analyzer-owned server persistence exists.

When scanner cache is enabled, analyzer stores MD5 content hashes under `kotlin:contentHash:MD5:<normalized input key>` solely for change detection; MD5 is not a trust or integrity mechanism. CPD tokens use `kotlin:cpdTokens:<input key>`. With unchanged-file skipping enabled by `sonar.kotlin.skipUnchanged`, or otherwise by scanner PR context, unchanged files reuse prior CPD tokens when available. Missing or malformed cached CPD entries cause reanalysis or omission of invalid cached tokens rather than analysis failure. SonarLint always analyzes selected main files and does not perform this incremental selection.

Cancellation stops before next file, returns incomplete status to progress reporter, and still disposes compiler resources.

## 6. Outputs

### 6.1 Native issues and suppression

Native findings use repository `kotlin` and active rule key. Primary location is exact syntactic or semantic evidence stated in catalog. Rules may attach secondary locations and remediation gap. Issues are not emitted for inactive rules.

Before checks, analyzer recognizes short annotation names `Suppress` and `SuppressWarnings`. String-literal or collection-literal arguments may name complete Sonar rule keys. Suppression applies within annotated element range. Compiler suppression aliases map as follows:

- `UNUSED_PARAMETER` to `kotlin:S1172`.
- `UNUSED_VARIABLE` to `kotlin:S1481`.
- `UNUSED` to both preceding keys.
- `TOO_MANY_ARGUMENTS` to `kotlin:S107`.
- `DEPRECATION` to `kotlin:S1874`.
- `UNCHECKED_CAST` and `CAST_NEVER_SUCCEEDS` to `kotlin:S6530`.
- `USELESS_CAST` and `USELESS_IS_CHECK` to `kotlin:S6531`.
- `VARIABLE_WITH_REDUNDANT_INITIALIZER`, `ASSIGNED_BUT_NEVER_ACCESSED_VARIABLE`, `UNUSED_VALUE`, and `UNUSED_CHANGED_VALUE` to `kotlin:S6615`.
- `UNNECESSARY_SAFE_CALL`, `UNNECESSARY_NOT_NULL_ASSERTION`, `USELESS_ELVIS`, and `USELESS_NULLABLE_CHECK` to `kotlin:S6619`.

Other literal arguments are treated as rule keys verbatim. Comments whose content begins with `NOSONAR`, ignoring case and surrounding whitespace, register all covered lines with platform no-Sonar filter and are not counted as comment lines.

### 6.2 Measures and line data

For each successfully parsed, nonblank main Kotlin file, analyzer emits:

- `ncloc`: unique source lines counted as code.
- `comment_lines`: comment and KDoc lines, excluding leading file-header comments and `NOSONAR` comments.
- `functions`: named functions with body.
- `classes`: Kotlin class declarations.
- `complexity`: one point for each named function with body, `if`, loop, `when` entry, and `&&` or `||` operation.
- `statements`: nondeclaration expressions in blocks and expression-bodied functions/properties, including unbraced conditional branches, `when` branches, and loop bodies.
- `cognitive_complexity`: analyzer's Kotlin cognitive-complexity result for whole file.
- `ncloc_data`: value 1 on every code line.
- `executable_lines_data`: value 1 on first line of executable statements in blocks, excluding package/import/class/function/block nodes themselves.

Metrics are not emitted for Gradle scripts because Gradle sensor has only check visitor. Android import telemetry becomes true when an import starts with `android` or `androidx`.

### 6.3 Syntax highlighting

Server analysis emits ranges for annotations, structured comments/KDoc, comments, keywords, constants, and string templates. A parent range prevents recursive child highlighting for that node. No highlighting is emitted by Gradle sensor or in SonarLint mode.

### 6.4 Duplication tokens

CPD excludes package directives, imports/import lists, file annotations, whitespace, comments, and KDoc. Remaining non-whitespace leaves become tokens. Entire string-template expression becomes one normalized token `LITERAL`, so string contents do not distinguish duplicates. Server analysis saves ranges and token text; SonarLint emits none.

### 6.5 Symbols

No production source creates a Sonar symbol table or reference index. Compatible implementation must not claim analyzer-owned symbol output.

### 6.6 Telemetry

On runtime API 10.9 or newer, project sensor emits `kotlin.android`, `kotlin.reports.surefire.classes.imported`, `kotlin.reports.surefire.classes.failed`, `kotlin.files.processed`, `kotlin.files.read.failures`, `kotlin.files.parse.failures`, `kotlin.scripts.processed`, `kotlin.scripts.read.failures`, and `kotlin.scripts.parse.failures`. Values are decimal strings; Android is `1` or `0`.

## 8. External issue imports

External repositories are available in SonarQube server mode, not SonarLint. For every shipped external key listed in section 9, analyzer-side detection semantics are identical: issue exists only when configured report contains finding with that key. Producing linter owns source-code detection, parameters, and exclusions. Analyzer does not rerun or reinterpret linter rule. Report message is primary message; report file and optional line determine location. Known key's shipped metadata supplies type, severity, and constant remediation effort. Unknown/custom keys are also accepted when report syntax is valid, using loader fallback classification; they are not part of shipped catalogs.

Report path properties accept absolute or base-relative paths through analyzer-commons report provider. Existing files are imported individually. Missing configured paths are skipped, logged, and produce one unique analysis warning naming count and property. Import continues for other existing reports.

### 8.1 Detekt

`sonar.kotlin.detekt.reportPaths` accepts Checkstyle XML. Root must be `checkstyle`; file `name` resolves against indexed absolute or relative paths. Each error requires nonempty `message`. `source` must begin `detekt.`; prefix is removed to form repository rule ID. Invalid prefix or missing message is skipped. Optional `line` selects whole line; column is ignored. Known metadata comes from 214-key `detekt` catalog. XML uses safe StAX factory.

### 8.2 ktLint

`sonar.kotlin.ktlint.reportPaths` dispatches strictly by lowercase filename extension: `.xml` uses Checkstyle importer; `.json` uses JSON importer; any other extension produces error and analysis warning. XML uses same file/message/optional-line mapping as Checkstyle. JSON root is array of objects containing `file` and `errors`; each finding supplies integer `line`, integer `column`, `message`, and `rule`. Column is accepted but location is whole line. Prefix `experimental:` is removed from rule ID in both formats. Invalid JSON logs error and imports no findings from that file. Known metadata comes from 86 distinct-key `ktlint` catalog. Its released resource contains each definition twice, yielding 172 identical records without creating additional rule IDs.

### 8.3 Android Lint

`sonar.androidLint.reportPaths` accepts Android Lint XML and is not restricted to Kotlin language at sensor-descriptor level. Root must be `issues`. Each `issue` supplies `id` and `message`; importer uses first nested `location` only. Required fields are ID, message, and file. Optional line selects whole line; column is ignored. Allowed target suffixes are `.xml`, `.java`, `.kt`, `.kts`, `.properties`, `.gradle`, `.cfg`, and `.txt`; binary files are skipped. Target must already be indexed and match absolute or relative path. Malformed report is logged and skipped. Known metadata comes from 444-key `android-lint` catalog. XML uses safe StAX factory.

## 10. Test execution reports and coverage

Surefire importer runs on Kotlin-language projects outside SonarLint. `sonar.junit.reportPaths` takes trimmed report directories relative to module base or absolute paths. Without property it scans `target/surefire-reports`. Missing user-configured directories log errors; missing default directory is silent. Within each directory importer first selects files beginning `TEST-` and ending `.xml`; only when none exist does it select `TESTS-` files. Empty matching directory warns.

StAX parser accepts descendant `testsuite` and `testcase` elements. Test class comes from testcase `classname`, or suite `name` when absent/blank. Parameterized classnames ending in closing parenthesis have parenthesized suffix removed. Nested class suffix after first `$` is merged into outer class report. Class name maps by dot-to-path conversion and `.kt` suffix against indexed files; first matching file receives measures. Unmatched classes increment failed-import telemetry and emit no measures.

For mapped classes with at least one test, analyzer emits `skipped_tests`, `tests`, `test_errors`, `test_failures`, and `test_execution_time`. `tests` excludes skipped count. Skipped duration is forced to zero. Other `time` values are parsed in English numeric locale and converted from seconds to integer milliseconds with three-decimal scaling. NaN becomes zero. Negative durations are excluded from total and cause warning that total may be inaccurate. `failure`, `error`, and `skipped` child states are distinguished; otherwise test passes. Malformed XML throws a report parse failure and aborts Surefire sensor.

Analyzer does not import coverage. Community Build's separate JaCoCo importer consumes Kotlin/JVM coverage. No Kotlin-specific coverage setting, report format, or fallback exists in this artifact.

## 11. Failures, partial results, and recovery

- Syntax error, missing PSI file, failed document mapping, content read exception, or other per-file parse/read exception logs file error, emits analysis error, increments appropriate telemetry, optionally raises active `kotlin:ParsingError`, and excludes that file from all later visitors. Other successfully loaded files continue.
- Compiler environment or K2 session construction failure can prevent semantic analysis for selected batch. Implementation must surface failure rather than silently invent syntax or semantic results.
- A visitor exception emits analysis error for file and logs visitor identity. Default behavior continues with later visitors and files, so earlier outputs may remain. With `sonar.internal.analysis.failFast=true`, same exception is rethrown as sensor failure after error recording.
- Unknown source-version value warns and recovers to Kotlin 2.4.
- Empty/whitespace file produces no visitor outputs and no issue.
- Cache read absence triggers normal analysis. Invalid CPD records are discarded individually. Cache write/copy collisions warn or debug-log and do not fail analysis.
- Missing external report files do not block valid report files. Unmapped report target skips findings for that file. Required-field failures skip individual finding.
- Detekt malformed Checkstyle file and Android Lint malformed XML are caught per report and logged. ktLint unsupported extension also adds analysis warning; malformed ktLint JSON logs and returns.
- Surefire malformed XML is fatal to Surefire sensor. Missing/unmatched test classes are partial import, reflected in telemetry.
- Cancellation stops remaining files, cancels progress, and cleans compiler resources.

## 12. Security and trust boundaries

Source, classpath, and report files are untrusted analysis inputs. Compatible implementation must parse but never execute project code or Gradle scripts. Compiler session reads source and library metadata only. Classpath filtering prevents arbitrary regular files from being treated as archives, but directories and ZIP/JAR contents remain untrusted and must be handled without class initialization.

External XML uses hardened safe StAX factory. Report paths cannot create findings on nonindexed files. Android importer restricts report targets to textual suffixes. Report-provided messages are data, not markup or executable content. Path matching accepts absolute or indexed relative identity and must not bypass scanner indexing or access control.

Content MD5 exists only to detect changes; it is not suitable for authenticity, security decisions, or hostile collision resistance. Security rules report potential vulnerabilities but do not alter analyzed application.

## 13. Compatibility and extension limits

Release plugin bytecode targets Java 11 and manifest advertises minimum Sonar version `6.7`, SonarLint support, and required language `kotlin`. Actual bundled deployment contract is Community Build 26.8.0.126808 and its plugin API/runtime. Analyzer embeds and repackages Kotlin compiler 2.4.0; independent implementation must preserve Kotlin 2.4 parse defaults and K2 semantic outcomes relevant to rules.

JVM analysis target remains 1.8 irrespective of scanner runtime Java. Kotlin language setting may request any version recognized by embedded 2.4 compiler. Unrecognized value falls back; no forward compatibility with post-2.4 syntax is implied.

`KotlinPluginExtensionsProvider` is explicitly experimental and has no compatibility guarantee. Provider must be public with public no-argument constructor and may register repositories/rule classes and optionally default-profile activation. Community artifact registers no added repository or rule through its own provider. Compatible Community implementation need not infer private/commercial providers.

Issue-message code-range formatting degrades to plain message when host API lacks formatting support; this compatibility fallback logs once and does not lose issue.

1. **Default Kotlin recognition.** Given indexed main `.kt`, main `.kts`, and test `.kt` files with default suffixes, run analysis. 4. **Version fallback.** Set unrecognized nonblank `sonar.kotlin.source.version`. Expected: warning names invalid value and analysis uses Kotlin 2.4. Set recognized older value: compiler uses that language/API version.
5. **Partial parser failure.** Provide one valid Kotlin file and one syntactically invalid file with `ParsingError` active. Expected: valid file completes; invalid file gets analysis error and `kotlin:ParsingError` on failing line when available, with no metrics/rules/CPD/highlighting for invalid file.
6. **Visitor isolation.** Cause one active check visitor to throw with fail-fast false. Expected: analysis error identifies file, later visitors/files continue. Repeat with fail-fast true: sensor fails after recording error.
7. **Suppression.** Annotate declaration with literal `kotlin:S1172` or compiler alias `UNUSED_PARAMETER`. Expected: S1172 finding whose primary range lies inside declaration is suppressed; unrelated rule outside range remains. 8. **Gradle root rules.** Set `sonar.kotlin.gradleProjectRoot` equal to base directory and omit both settings filenames plus verification metadata. Activate S6631 and S6474. Expected: two project-level issues. Set root to different module directory: no project-level check there.
9. **Gradle script rules.** Analyze Android application `build.gradle.kts` whose release block resolves debug true and lacks valid minification/proguard setup. Expected: S7416 on debug assignment and S7204 on relevant release configuration. Same constructs in `settings.gradle.kts` or Android library without application ID are excluded.
10. **Measures and CPD.** Analyze valid main Kotlin with functions, branches, comments, string templates, imports, and package. Expected: listed measures/line data follow section 6; CPD excludes package/import/comments and replaces each whole string template with `LITERAL`.
11. **Incremental reuse.** In skip-unchanged context with matching content hash and valid prior CPD token cache, rerun unchanged file. Expected: no full Kotlin visitor run for file; prior CPD tokens are copied to new output/cache. Missing prior tokens cause analysis rather than silent loss.
12. **Surefire precedence.** Directory contains both `TEST-` and `TESTS-` XML. Expected: only `TEST-` set is parsed. A nested test class maps to outer `.kt`; skipped tests reduce `tests` and contribute `skipped_tests` with zero duration.
13. **Detekt import.** Configure valid Checkstyle report containing source `detekt.EqualsWithHashCodeExist`, message, file, and line. Expected: external issue engine `detekt`, rule ID without prefix, catalog classification, message, and whole-line location. Source lacking `detekt.` is skipped.

15. **Android Lint import.** Report issue with two locations, first indexed text file and second another file. Expected: only first location is used. Binary suffix, missing ID/message/file, or nonindexed target is skipped; unknown/custom ID is still accepted with fallback classification.
16. **Coverage boundary.** Supply only JaCoCo XML without bundled JaCoCo integration. Expected: Kotlin analyzer emits no coverage. With JaCoCo integration enabled, coverage belongs to integration contract, not this analyzer.
17. **SonarLint mode.** Analyze main Kotlin in SonarLint. Expected: native rules and metrics run; CPD, highlighting, Surefire, and external-report definitions/sensors do not run.
