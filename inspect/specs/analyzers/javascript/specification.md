# JavaScript Analyzer Specification

## Identity, license, and authority

This specification covers JavaScript repository key `javascript`, language key `js`, in bundled artifact `org.sonarsource.javascript:sonar-javascript-plugin:13.4.0.43982:multi`. SonarQube Community Build `26.8.0.126808` bundles that exact artifact. Authoritative source is SonarSource/SonarJS tag `13.4.0.43982`, commit `d02b514f8007f18a798876fc9361b9c233ab2f02`. Analyzer-owned source is under Sonar Source-Available License v1.0 (`LicenseRef-SSAL-1.0`); packaged dependencies retain their own notices. This is a clean-room behavior specification, not legal advice. [I1][I2]

## Purpose, scope, and ownership

The analyzer recognizes JavaScript, JSX, CommonJS and ECMAScript module variants, and Vue single-file components; parses them; runs active JavaScript rules; emits issues and quick fixes; computes file measures, highlighting, symbols, executable lines, and duplication tokens; imports LCOV and ESLint reports; and exposes AST results to registered analysis consumers. TypeScript rule semantics belong to `../typescript/specification.md`; CSS belongs to `../css/specification.md`; extraction and host-coordinate projection for HTML/YAML and embedded styles belongs to `../embedded-web-yaml/specification.md`. Platform profiles, metric definitions, issue lifecycle, persistence, and report transport remain platform-owned contracts. [B2][R3][M1]

Commercial rule bundles and private analyzers are excluded. The packaged ESLint plugin distribution, build/test tooling, telemetry back end, and third-party parser implementations are dependencies rather than independently re-specified products. [I1]

## Shared bridge and runtime contract

This section is authoritative for JavaScript, TypeScript, CSS, and embedded Web/YAML specifications; dependent files reference it and do not redefine it.

One project sensor selects `js`, `ts`, `css`, `web`, and eligible `yaml` inputs, collects active JavaScript/TypeScript and CSS rule configurations plus project metadata, starts a Node.js analysis runtime lazily, and sends one project request over a plaintext gRPC channel bound to the loopback address. Results stream per file and terminate with project metadata; missing terminal metadata is a project failure. Cancellation is checked before startup and during streaming, cancels transport, and is reported as cancellation rather than a rule failure. [B1][B2]

Runtime selection precedence is `sonar.nodejs.executable`, then provisioned embedded runtime, then host runtime. `sonar.scanner.skipNodeProvisioning=true` skips embedded deployment; deprecated `sonar.nodejs.forceHost` takes precedence over that property when present. Supported runtime minima derived from `package.json` are 20.12.0, 22.11.0, and 24.0.0 by major line; versions below 20.12.0 fail, while a newer unsupported major/minor can run with a warning. Embedded binaries are available for Windows x64, Linux arm64, Linux x64 glibc, Linux x64 musl, macOS arm64, and macOS x64. They are extracted under `sonar.userHome/js/node-runtime` with version checking and a 10-second extraction-lock wait; deployment failure cleans partial runtime files and falls back to host Node. [B1]

Startup has a 300-second bridge timeout. `sonar.javascript.node.maxspace` adds a Node old-space limit; `sonar.javascript.node.debugMemory` enables memory diagnostics; `sonar.javascript.node.timeout` defaults to 15,000 ms for an unleased child runtime shutdown. `SONARJS_EXISTING_NODE_PROCESS_PORT` attaches to an externally managed runtime and disables child-process lease ownership. Analyzer-started runtimes acquire a bidirectional lease, are considered alive only while channel and lease are alive, and are stopped with the plugin. A failed runtime is not immediately retried; restart becomes eligible only after a prior healthy state has been absent for more than 60 seconds. [B1]

The bridge deploys active external rule bundles into a temporary work area, sends enabled rules and file/project inputs, and receives issues, suppressed issues, parsing failures, measures, highlights, symbols, CPD tokens, optional AST, warnings, and telemetry. UTF-8 SonarQube files may be read by runtime filesystem access rather than copied into request; SonarLint and non-UTF-8 files send content. `sonar.javascript.canAccessFileSystem=false` forces indexed metadata files (`tsconfig.json`, `package.json`, `deno.json`, `deno.jsonc`, `pnpm-workspace.yaml`) into request. [B2]

No analyzer result is durable by itself. Scanner cache strategy applies to indexed `js`, `ts`, `web`, and `yaml` files. On a JavaScript/TypeScript cache hit, only CPD tokens and optional AST are replayed; cached Web/YAML hosts emit no adapter result for that unchanged file. Pure CSS and extension-selected inputs outside those indexed language keys are reanalyzed. SonarQube program caches are cleared after project analysis; SonarLint retains incremental program and tsconfig caches until base directory, configuration, or file events invalidate them. [B2][T1]

## Inputs, recognition, and precedence

Language key is `js`. `sonar.javascript.file.suffixes` defaults to `.js,.jsx,.cjs,.mjs,.vue`. Configured suffixes are trimmed, lower-cased, prefixed with a dot when absent, de-duplicated in first-seen order, and replace defaults. A Vue file containing a script tag whose `lang` attribute is `ts` is analyzed through TypeScript parsing even though scanner language remains JavaScript. [B2]

JavaScript/TypeScript exclusions share one combined surface. Defaults are `**/.git/**`, `**/node_modules/**`, `**/bower_components/**`, `**/dist/**`, `**/vendor/**`, `**/external/**`, `**/contrib/**`, and `**/*.d.ts`. If either `sonar.javascript.exclusions` or `sonar.typescript.exclusions` is explicitly present, their nonblank values are concatenated and replace all defaults. `.scannerwork` remains forcibly ignored. Platform `sonar.sources`, `sonar.tests`, inclusion, and exclusion settings classify main/test inputs before rule scope is applied. [B2]

JavaScript and TypeScript files are excluded when UTF-8 byte size exceeds `sonar.javascript.maxFileSize`, default 1000 kB; minified names ending in `.min.js` or `-min.js` and `.js` content averaging more than 200 characters per line are excluded. Bundle detection, enabled by default and disabled with `sonar.javascript.detectBundles=false`, inspects the first 2,048 characters for a bundled wrapper signature. `sonar.javascript.detectGeneratedCode`, default true, detects GraphQL Code Generator, OpenAPI Generator, and proto-loader generated families and suppresses only rules tagged to skip editable generated source; it does not remove every generated file from analysis. A noninteger `sonar.javascript.maxFileSize` warns and falls back to 1000. Compatibility quirk: a parsed zero or negative value is warned as invalid but remains forwarded, causing every nonnegative-size JS/TS file to exceed the resulting threshold. [B2]

Parser precedence is TypeScript parser first when internal `allowTsParserJsFiles` is true (default) or input is TypeScript; JavaScript falls back to bundled Babel parser in module mode, then script mode. Vue uses `vue-eslint-parser` with JavaScript or TypeScript script parser. Project `package.json`, Deno metadata, dependency manifests, module type, detected ECMAScript library year, and active quality-profile configuration can enable or suppress individual rules. `sonar.javascript.environments` defaults to amd, applescript, atomtest, browser, commonjs, embertest, greasemonkey, jasmine, jest, jquery, meteor, mocha, mongo, nashorn, node, phantomjs, prototypejs, protractor, qunit, serviceworker, shared-node-browser, shelljs, webextensions, worker. `sonar.javascript.globals` defaults to angular, goog, google, OpenLayers, d3, dojo, dojox, dijit, Backbone, moment, casper, underscore, sap. [B2][R2]

JavaScript files can participate in TypeScript programs when compiler configuration includes them. `sonar.javascript.disableTypeChecking=false` and `sonar.javascript.createTSProgramForOrphanFiles=true` are defaults. Disabling type checking forces syntax-only analysis. With orphan program creation enabled, uncovered JavaScript/TypeScript files receive fallback programs grouped by effective library; disabling it leaves them syntax-only. Valid `sonar.javascript.ecmaScriptVersion` overrides tsconfig target and package Node signals for library selection. [T1]

## Processing and outputs

For each accepted file, analyzer builds parser source model, initializes dependency-aware rule configuration, runs active rules matching language, scope, dependency, ECMAScript, module, generated-source, and type-information gates, then collects outputs. Main files produce issues, quick fixes, `functions`, `statements`, `classes`, `complexity`, `cognitive_complexity`, `ncloc`, `comment_lines`, per-line `ncloc_data`, `executable_lines_data`, syntax highlighting, symbol declaration/reference groups, and CPD tokens. Test files can produce rules whose scope permits tests plus highlighting and symbols, but SonarQube persists no structural measures or CPD for tests. SonarLint persists issues and NOSONAR handling, not server measures or CPD. [M1][B2]

Function count includes declarations, expressions, and arrows. Statement count covers executable statement forms defined by parser AST. Class count includes declarations and expressions. Cyclomatic complexity increments for functions, loops, conditionals, switch cases, conditional expressions, and logical expressions; cognitive complexity comes from the analyzer's cognitive-complexity collector. NCLOC is token-line based. Nonempty comments contribute comment lines unless `sonar.javascript.ignoreHeaderComments=true` (default) and they precede first token. A comment whose trimmed text begins with `NOSONAR`, case-insensitively, suppresses issues on its covered lines rather than adding comment-line measure. [M1]

Highlight types are `KEYWORD`, `STRING`, `CONSTANT`, `COMMENT`, and `STRUCTURED_COMMENT`. Symbol groups cover declared variables and their references, paired braces, and Vue opening/closing tags. CPD omits import declarations and supported `require` variable declarations, normalizes non-JSX string literals to one literal image, and retains other token images. CPD persistence failure is nonfatal for project but disables duplication analysis for that file; invalid individual highlights or issue locations are warned and remaining outputs continue. [M1][B2]

Issues carry fully qualified repository key, primary range, optional secondaries, message, optional effort gap, and quick-fix edits. Quick fixes are exposed when implementation metadata supplies one; SonarQube API 9.2 or later marks availability, and compatible SonarLint API receives edits. Parser failure stops ordinary outputs for that file, records an analysis error, and raises `javascript:S2260` only when active. Valid parser columns select one character; invalid ranges fall back to line or file start. [B2]

## Coverage and external reports

`sonar.javascript.lcov.reportPaths` and alias `sonar.typescript.lcov.reportPaths` accept multiple absolute, relative, or wildcard LCOV paths. Values from both keys are set-unioned and merged. Import runs only for main `js`/`ts` files when at least one key is present. `SF`, `DA`, and `BRDA` records map source paths to indexed files; repeated records merge line hits and branch observations. Missing reports produce no coverage; unresolved source paths and malformed/inconsistent records are warnings while resolvable coverage remains. [L1]

`sonar.eslint.reportPaths` accepts multiple ESLint JSON reports in SonarQube, not SonarLint. Each record supplies file path and messages with `ruleId`, message, start and optional end positions. Relative paths resolve first against report provider base, then indexed path. Null `ruleId` parse errors are skipped. Missing files, unreadable JSON, and invalid JSON warn and preserve other reports. Within importer aggregation, a later file record/report for the same indexed path replaces the earlier pending ESLint list before native deduplication. Zero-length or start-only locations expand to whole line. Imported issues use engine/repository `eslint_repo`; 1,177 packaged ESLint identifiers span core, `@angular-eslint`, `@angular-eslint/template`, `@typescript-eslint`, angular, ember, flowtype, import, jsx-a11y, node, promise, react, react-hooks, sonarjs, and vue catalogs. An imported issue is discarded when native analysis reports the same ESLint key, normalized file path, and exact range. [X1]

## Failure, recovery, and security boundaries

Having no selected inputs is a successful no-op. Scanner cancellation is a successful interruption with no further rule work. Missing/unsupported Node, missing explicit executable, bridge startup timeout, malformed project request, runtime internal/resource exhaustion, unresponsive channel, absent final metadata, or unrecoverable project exception fails JS/TS analysis. A per-file runtime error records an analysis error and continues other files unless internal fail-fast is enabled. Parser failure is file-local. Invalid tsconfig is warning and remaining configs/orphan fallback continue. [B1][B2][T1]

Project source, dependency manifests, tsconfig inheritance, external report paths, and rule bundles are untrusted inputs. Implementations must confine analyzer transport to loopback, validate message fields and source ranges before platform writes, avoid Windows current-directory executable lookup, normalize report/source paths against indexed files, and never execute project scripts merely to discover metadata. Explicit `sonar.nodejs.executable`, external bridge port, and report paths cross operator trust boundaries. [B1][B2][X1]

## Compatibility and limits

Plugin descriptor requires Java 17, plugin API minimum `9.14.0.375`, and languages `js,ts,css,web,yaml`; it advertises SonarLint support. Bundled runtime dependencies include TypeScript 6.0.3, ESLint 9.39.5, Babel 8.0.1, `@typescript-eslint` 8.65.0, `vue-eslint-parser` 10.4.1, and Node engine lines 20/22/24. Exact parser acceptance and third-party rule behavior must remain compatible with those pinned versions. [I1][B1]

## Acceptance scenarios

1. With no suffix override, a main `.mjs` file is indexed as `js`, parsed, checked by active JavaScript rules, and emits full main-file measures, highlighting, symbols, and CPD.
2. When either language-specific exclusion property is present, defaults are replaced by concatenated configured JavaScript and TypeScript patterns; a file matching the resulting set is not analyzed.
3. A `.min.js` file or `.js` file whose average line length exceeds 200 is skipped; a large CSS file is not skipped by this JavaScript size gate.
4. With default orphan-program creation and type checking, a JavaScript file absent from every tsconfig is included in a fallback TypeScript program with JavaScript enabled and can supply parser services to type-dependent rules. It becomes syntax-only when type checking or orphan-program creation is disabled.
5. An active rule with a generated-source skip tag does not run on a detected generated family when detection is enabled; other active rules still run.
6. A parser error records file analysis error and, when `javascript:S2260` is active, one parser-failure issue at best valid host location; no ordinary file artifacts are accepted.
7. LCOV reports configured through both JavaScript and TypeScript keys merge; resolvable records save coverage and unresolved paths only warn.
8. An ESLint issue identical in key, file, and range to native issue is not imported; a same-message issue at another range remains external.
9. Scanner cancellation terminates stream and does not convert cancellation into analysis failure.
10. An explicit nonexistent `sonar.nodejs.executable` fails immediately instead of falling back to embedded or host runtime.
