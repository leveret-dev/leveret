## 2. Purpose, ownership, and exclusions

The family analyzes C# and VB.NET compilations through Roslyn, emits native Sonar issues, imports third-party Roslyn diagnostics, and supplies source measures, highlighting, symbol references, duplication tokens, generated-file metadata, coverage, and unit-test results. C# and VB.NET have separate language keys, rule repositories, profiles, file recognition, syntax semantics, and rule catalogs, while sharing report transport and import behavior.

This specification owns only .NET language recognition and analysis outputs. Plugin discovery, profile storage, active-rule delivery, scanner report transport, issue persistence and lifecycle, quality gates, and metric persistence belong to the platform contract owners in `manifest/dependency-map.md`. SonarScanner for .NET orchestration is a required producer of project configuration and analyzer reports but is not bundled here. Compiler implementation, MSBuild, test runners, coverage tools, commercial security and taint analyzers, private commercial rule repositories, and server-side issue lifecycle are excluded. `.cshtml` host-file metrics remain owned by the HTML analyzer; this family only accepts mapped C# diagnostics and cache entries for that format.

## 4. Language and file recognition

### 4.1 C#

C# uses language key `cs`, language name `C#`, and default suffixes `.cs,.razor`. `sonar.cs.file.suffixes` replaces that suffix list when configured. Roslyn-generated `.razor.g.cs` and `.cshtml.g.cs` trees are recognized through case-insensitive generated-name patterns and mapped line information. `.cshtml` is recognized by analyzer path helpers and by the C# scanner cache, but it is not a default C# indexed suffix and does not receive C# metrics because the HTML analyzer owns the host file. Utility output generation also permits `.csx`, but `.csx` is not a default indexed suffix; full analysis therefore requires an upstream scanner configuration that indexes it as C#.

`sonar.cs.analyzeRazorCode` defaults to `true`. When true, mapped Razor C# is fully analyzed. When false, Community Build must not claim full Razor analysis; the plugin description reserves `.cshtml` processing for security-only behavior supplied elsewhere. Build-time Razor diagnostics require a mapped path and are projected to the host file. Design-time Razor diagnostics require mapped paths, Roslyn 4.9.2 or newer, and are suppressed for rule keys `S108`, `S927`, `S1144`, `S1481`, `S1871`, `S2259`, `S2325`, `S2696`, `S4487`, and duplicate-listed `S1481`.

### 4.2 VB.NET

VB.NET uses language key and repository key `vbnet`, language name `VB.NET`, and default suffix `.vb`. `sonar.vbnet.file.suffixes` replaces that list when configured. VB syntax trees, symbols, case-insensitive name comparison, executable statements, and generated-code recognition use the Visual Basic Roslyn model. Razor analysis is always false for VB.NET.

### 4.3 Language-version behavior

No independent maximum analyzed-language version is declared. A file is analyzable when the invoking Roslyn host can parse it and construct the semantic model used by the rule. Newer syntax is accessed through light-up wrappers where supplied. Unsupported or erroneous syntax may produce incomplete semantic information; individual rules must avoid fabricating findings when required symbols or operations are unavailable. The analyzer records the C# parse-option language version as telemetry but does not use telemetry as an acceptance gate.

*Provenance:* `sonar-csharp-core/src/main/java/org/sonarsource/csharp/core/CSharpCorePluginMetadata.java`; `sonar-vbnet-core/src/main/java/org/sonarsource/vbnet/core/VbNetCorePluginMetadata.java`; `analyzers/src/SonarAnalyzer.Core/Common/AnalyzerLanguage.cs`; `analyzers/src/SonarAnalyzer.Core/Syntax/Utilities/GeneratedCodeRecognizer.cs`; `analyzers/src/SonarAnalyzer.Core/AnalysisContext/IssueReporter.cs`; `sonar-csharp-core/src/main/java/org/sonarsource/csharp/core/CSharpPropertyDefinitions.java`.

## 6. Roslyn processing pipeline and lifecycle

1. The host compiler creates one language compilation with project references, parse options, generated trees, and additional configuration files. The analyzer reads `SonarProjectConfig.xml`, `SonarLint.xml`, analysis configuration, and file lists when supplied by Scanner for .NET.
2. Every normal rule registers Roslyn compilation, syntax-tree, syntax-node, symbol, operation, code-block, or semantic-model actions as required. Rules may use semantic symbol resolution, constant values, control-flow graphs, live-variable analysis, and compilation-wide aggregation. No project source is executed.
3. Before reporting, the common context enforces project scope, generated-code policy, file inclusion, valid source locations, Razor mapping, and Roslyn’s configured rule activation. Scanner-run test projects execute utility analyzers and rules marked `Tests`; ordinary `All` rules do not run there until the server supports them as first-class test-code rules. In standalone/IDE analysis, declared `All`, `Main`, and `Tests` tags are respected directly.
4. Normal rule analyzers request concurrent Roslyn execution by default. Environment variable `SONAR_DOTNET_ENABLE_CONCURRENT_EXECUTION=false` disables it. Utility analyzers intentionally serialize their output generation and write one length-delimited protobuf stream per output kind at compilation end.
5. Per project, analyzer output is written below `output-cs` or `output-vbnet`. The plugin first consumes `file-metadata.pb` globally so scanner file filters know generated status and Roslyn-detected encoding. Module sensors collect project types and report paths. The final project sensor imports metrics before issues so `NOSONAR` lines can suppress applicable issues, then imports highlighting, symbols, CPD tokens, and Roslyn/SARIF issues.
6. Imports aggregate across all MSBuild projects in the solution. Metrics and CPD generally apply to MAIN code only; test-method declarations apply to test code. Highlight and symbol streams merge multiple project contributions. Duplicate source messages are suppressed according to section 11.

Output stream names are `metrics.pb`, `token-type.pb`, `symrefs.pb`, `token-cpd.pb`, `file-metadata.pb`, `test-method-declarations.pb`, `log.pb`, and `telemetry.pb`. Text ranges are one-based by line, zero-based by line offset, and have inclusive end lines.

*Provenance:* `analyzers/src/SonarAnalyzer.Core/Analyzers/SonarDiagnosticAnalyzer.cs`; `analyzers/src/SonarAnalyzer.Core/Rules/Utilities/UtilityAnalyzerBase.cs`; `analyzers/src/SonarAnalyzer.Core/Protobuf/AnalyzerReport.proto`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/ModuleConfiguration.java`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/ProtobufDataImporter.java`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/sensors/DotNetSensor.java`.

## 7. Generated code, Razor, encoding, and scanner cache

A file is generated when its case-insensitive filename contains `.g.`, `.generated.`, `.designer.`, `_generated.`, `temporarygeneratedfile_`, or `.assemblyattributes.vb`; when a leading comment contains `<auto-generated`, `<autogenerated`, or `generated by`; or when its syntax carries `DebuggerNonUserCode`, `GeneratedCode`, or `CompilerGenerated` attributes, including `Attribute` suffix forms. File metadata is always produced for ordinary compiler trees even when generated-code analysis is disabled. With `analyzeGeneratedCode=false`, the scanner filter excludes recognized generated input files and normal rule actions skip generated trees. With the setting true, normal generated files are eligible.

Razor-generated C# is a deliberate exception: mapped Razor may be analyzed even though its compiler tree is generated. Metrics use host-file mapped paths and exclude imported Razor content not mapped to the same host. C# highlighting and CPD do not process generated Razor trees. `.cshtml` never receives C# metrics. Invalid issue ranges for `.razor` and `.cshtml` may degrade to a whole line or file rather than aborting import.

Roslyn’s per-file encoding is compared with scanner encoding before indexing. Unknown Roslyn encoding falls back to scanner encoding. UTF-16 and UTF-16LE are treated as compatible. Any other mismatch excludes the file and records a warning. Path and URI comparisons used for generated status and encoding are case-insensitive because Windows paths may differ only by case.

During ordinary Community analysis, an enabled scanner cache with a scanner-supplied common base path stores hashes under normalized relative paths for indexed language files; C# additionally hashes `.cshtml`. A missing base path or disabled cache leaves analysis results unchanged and produces no cache entries. Failure to hash one file records a warning and does not discard successful entries for other files. Cache data is replaceable optimization state and never changes rule, measure, or issue semantics.

*Provenance:* `analyzers/src/SonarAnalyzer.Core/Syntax/Utilities/GeneratedCodeRecognizer.cs`; `analyzers/src/SonarAnalyzer.Core/Extensions/IAnalysisContextExtensions.cs`; `analyzers/src/SonarAnalyzer.Core/Rules/Utilities/FileMetadataAnalyzerBase.cs`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/filters/GeneratedFileFilter.java`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/EncodingPerFile.java`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/sensors/AbstractFileCacheSensor.java`.

## 8. Metrics

The family emits these public core measures or line-data keys for eligible MAIN files: `classes`, `statements`, `functions`, `complexity`, `comment_lines`, `ncloc`, `ncloc_data`, `cognitive_complexity`, and `executable_lines_data`. It also registers lines containing `NOSONAR` with the platform issue filter. Code lines are distinct mapped lines containing non-end-of-file tokens. Nonblank comment lines require a letter or digit; a line containing `NOSONAR` is excluded from comment-line count and instead becomes a suppression line. `sonar.<language>.ignoreHeaderComments=true` omits leading header trivia.

C# class count includes classes, records, structs, record structs, and interfaces mapped to the same host file. Function count includes implemented methods, constructors, destructors, operators, conversion operators, local functions, expression-bodied properties, and accessors, including implicit concrete accessors but excluding abstract/interface declarations and unmapped Razor members. Statement count covers executable C# statements and excludes block containers. Cyclomatic complexity increments for implemented callable/accessor entry points and decision constructs including conditionals, loops, conditional access, coalescing, logical operators, switch labels/arms, and binary patterns.

VB.NET class count includes classes, structures, interfaces, and modules. Function count includes implemented constructors, subs, functions, operators, and property/event accessors, excluding interface members, declaration-only members, and `MustOverride` members. Every Roslyn `ExecutableStatementSyntax` contributes to statement count. VB cyclomatic complexity counts functions and its language-specific branch, loop, exception, error-handling, jump, continuation, Boolean short-circuit, and termination constructs. Both languages compute cognitive complexity with language-specific nesting and recursion rules and compute executable lines from semantic syntax rather than treating every code line as executable.

A metric message with an out-of-range code line ignores that line and continues. Negative cognitive complexity is not saved. Missing `metrics.pb` yields no .NET measures and a warning; it does not synthesize zero values for absent files.

*Provenance:* `analyzers/src/SonarAnalyzer.Core/Metrics/MetricsBase.cs`; `analyzers/src/SonarAnalyzer.CSharp/Metrics/CSharpMetrics.cs`; `analyzers/src/SonarAnalyzer.CSharp/Metrics/CSharpCyclomaticComplexityMetric.cs`; `analyzers/src/SonarAnalyzer.VisualBasic/Metrics/VisualBasicMetrics.cs`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/protobuf/MetricsImporter.java`.

## 9. Highlighting, symbols, and duplication

Highlighting classifies numeric literals as constants, comments as comments, language keywords and preprocessor directives as keywords, type names as light keywords, and string/character/interpolated literal parts as strings. Semantic type-name classification is skipped after more than 4,000 identifier tokens in a file; lexical keywords and literals remain. Generated Razor trees are excluded. Multiple project streams are deduplicated before one highlighting object is saved per file. An invalid range is skipped; overlapping or otherwise invalid final highlighting causes a hard import error with a warning that build-time and scan-time contents must match.

Symbol tables connect declarations to references within the same file. C# declarations include types, delegates, events, methods, properties, parameters, locals, type parameters, records, local functions, and single-variable designations. VB.NET includes types, events, fields, methods, properties, parameters, locals, and type parameters. Partial symbol parts are joined when they map to the same file. Files over 40,000 tokens receive no symbol-reference output. Invalid references and references overlapping their declaration are dropped; missing declarations prevent a symbol entry.

CPD excludes C# `using` directives and VB.NET `Imports` statements. Numeric, string, and character literal values are normalized to common token classes; other tokens retain textual identity. CPD is not emitted for test projects or generated Razor trees, and server-side duplication thresholds remain a platform concern. Out-of-range token ranges are skipped while valid tokens are saved.

*Provenance:* `analyzers/src/SonarAnalyzer.Core/Rules/Utilities/TokenTypeAnalyzerBase.cs`; `analyzers/src/SonarAnalyzer.Core/Rules/Utilities/SymbolReferenceAnalyzerBase.cs`; `analyzers/src/SonarAnalyzer.Core/Rules/Utilities/CopyPasteTokenAnalyzerBase.cs`; language-specific utility analyzers under `analyzers/src/SonarAnalyzer.CSharp/Rules/Utilities/` and `analyzers/src/SonarAnalyzer.VisualBasic/Rules/Utilities/`; protobuf importers under `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/protobuf/`.

## 10. Coverage and unit-test report imports

### 10.1 Coverage

Each language exposes five additive, multi-valued project properties: `sonar.<language>.ncover3.reportsPaths`, `.opencover.reportsPaths`, `.dotcover.reportsPaths`, `.vscoveragexml.reportsPaths`, and `.cobertura.reportsPaths`, where `<language>` is `cs` or `vbnet`. Values may be exact paths or wildcard patterns relative to the process working directory. All configured formats are aggregated; no format has precedence. Duplicate report parsing is cached, line hits are summed, and branch observations are merged conservatively by taking the greatest per-format total and covered count, capped so covered conditions never exceed total conditions.

- NCover3 requires a `coverage` root and export version 3, imports document and sequence-point line hits, ignores document ID `0` and line `0`, and always emits a deprecation warning.
- OpenCover requires a `CoverageSession` root, imports files, sequence points, and branch points, supports a current `FileRef`, and attempts deterministic-build path resolution when the absolute path is not indexed.
- dotCover accepts its HTML report, resolves the source path from the page title, and imports line/hit ranges. It does not import branch conditions.
- Visual Studio coverage XML requires a `results` root. `yes` and `partial` ranges count as covered; `no` counts as uncovered; any other coverage value fails that report.
- Cobertura requires a `coverage` root, resolves class filenames against declared sources, imports line hits, and imports jump/switch conditions when branch metadata is usable. Unknown condition types or unresolvable files are skipped.

Only indexed MAIN files of the matching language receive coverage. TEST files, other-language files, excluded files, and paths outside the solution are skipped. Out-of-range line hits are omitted and cause a warning; valid data for the same report still saves. A configured pattern matching no files creates an analysis warning. A malformed report is isolated: that report is skipped and other reports continue. If no included MAIN file receives data, the sensor warns instead of inventing coverage.

### 10.2 Unit tests

Each language exposes `sonar.<language>.vstest.reportsPaths`, `.nunit.reportsPaths`, and `.xunit.reportsPaths`. All configured reports aggregate by source file. Roslyn first emits assembly, type, and method declarations for test projects. Importers match test identities to those declarations and sum `tests`, `test_errors`, `test_failures`, `skipped_tests`, and `test_execution_time` in milliseconds. Unmatched tests do not create project-level synthetic measures.

Visual Studio TRX accepts `TestRun`, associates `UnitTestResult` records with `UnitTest`/`TestMethod` metadata, and derives duration from start and end timestamps. NUnit accepts version 2 `test-results` and version 3 `test-run` roots, reads assembly suites and test cases, and converts seconds to milliseconds. xUnit accepts `assembly` or `assemblies`, reads test type/method identity and seconds-based time. A malformed report is logged and skipped while other reports continue. A failure outside the per-report parser prevents that language’s unit-test import, records one analysis warning, and does not discard already imported non-test analysis outputs.

*Provenance:* `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/CodeCoverageProvider.java`; coverage parsers under `sonar-dotnet-core/src/main/java/org/sonar/plugins/dotnet/tests/coverage/`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/UnitTestResultsProvider.java`; test parsers under `sonar-dotnet-core/src/main/java/org/sonar/plugins/dotnet/tests/`.

## 11. Native and external issue import, locations, and custom rules

The plugin reads scanner-supplied Roslyn JSON reports. Versions `0.1` and `0.4` use the legacy parser; every other declared version uses the 1.0-shaped parser. Suppressed-in-source results are ignored. A result with one valid physical location becomes a ranged issue; no usable location becomes a project- or file-level issue. Related locations become secondary locations, or a reversed execution flow when `secondaryLocationAsExecutionFlow` is true. Missing indexed files cause the issue to be skipped.

An active rule ID in `csharpsquid`, `vbnet`, or any repository whose key begins `roslyn.` is imported as a native Sonar issue under that repository. The same rule ID must not be active in two such repositories; duplication is a hard configuration error. Native issue metadata comes from the registered Sonar rule. The import de-duplicates ranged issues by rule and exact primary range, file-level issues by rule and path, and project issues by rule and message.

An unknown rule becomes an external issue only when third-party imports are enabled and the ID does not match `S` followed by three or four digits. External engine ID is `roslyn`. SARIF rule metadata creates an ad hoc rule. Category mapping first tests the configured Bug, Code Smell, and Vulnerability category sets in that order; otherwise `error` becomes Bug and every other level becomes Code Smell. Severity maps `error` to Critical, `warning` to Major, and other values to Info. If neither result nor rule supplies a level, severity is Major. On Community Build, type also maps to Reliability, Maintainability, or Security impact with Critical/High, Major/Medium, Minor/Low, Blocker/Blocker, and Info/Info severity correspondence.

Precise locations are zero-based by column after conversion and one-based by line. For external rules and Razor host files, an invalid range falls back first to the reported line and then to file level. Invalid locations from this family’s non-Razor native rules are not silently repaired. Secondary locations whose files are absent are omitted. Rules `S3904`, `S3990`, `S3992`, and C# `S4026` attach only to the project component and name the assembly in their message. VB.NET `S6145` and `S6146` attach to an offending option statement when present and can also attach to the project component for an incompatible compilation option.

Custom-rule integration has two supported contracts. A Roslyn analyzer may publish rule definitions through a `roslyn.*` repository, participate in active-rule delivery, run in the Scanner for .NET compiler invocation, and emit its diagnostics into the same report; the importer then treats active IDs as native rules and inactive unknown IDs as external rules according to the policy above. Separately, server-side `ProfileRegistrar` extensions may add arbitrary repository/rule keys to the C# or VB.NET built-in `Sonar way` profile. Neither contract permits a custom rule to replace a shipped rule ID or bypass the unique-ID check.

*Provenance:* `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/RoslynDataImporter.java`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/SarifParserCallbackImpl.java`; SARIF parsers under `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/sarif/`; `sonar-csharp-core/src/main/java/org/sonar/plugins/csharpenterprise/api/ProfileRegistrar.java`; `sonar-vbnet-core/src/main/java/org/sonar/plugins/vbnetenterprise/api/ProfileRegistrar.java`.

## 12. Shipped C# rule catalog

This catalog is the intersection of the C# metadata and the `Rules.json` embedded in the released C# JAR. It contains 456 released keys: 339 Code Smells, 81 Bugs, and 36 Vulnerabilities. “Sonar way” denotes default built-in-profile activation after packaged-catalog filtering. Scope is `Main`, `Tests`, or `All`; during Scanner for .NET test-project analysis, section 6 further restricts ordinary `All` rules. Unless a rule is explicitly project-level, its primary location is the precise Roslyn range selected by the rule; a rule may also provide secondary ranges or an execution flow. Entry-specific exclusions below summarize only documented exception sections; all entries also obey shared file, generated-code, activation, and scope filters.

*Per-entry provenance:* shipped membership and parameters: official C# JAR member `org/sonar/plugins/csharp/Rules.json`; metadata: `analyzers/rspec/cs/<key>.json`; detection and documented exclusions: `analyzers/rspec/cs/<key>.html` and corresponding analyzer under `analyzers/src/SonarAnalyzer.CSharp/Rules/` or shared base under `analyzers/src/SonarAnalyzer.Core/Rules/`.

- `S100` — Reports methods or properties whose names do not use PascalCase. Type `CODE_SMELL`; default severity `Minor`; scope `All`; status `ready`; Sonar way `no`; location: primary diagnostic range on the offending construct; parameters: none; exclusions: Does not report ComImportAttribute or InterfaceTypeAttribute members, extern methods, names containing '_', permitted custom acronyms, or two consecutive uppercase characters unless they comprise the entire name.
- `S101` — Reports types whose names do not use PascalCase. ## 14. Failure, partial-result, and recovery behavior

- If language files are indexed without any Scanner for .NET project, the sensor warns that Scanner for .NET 5.x or newer is required and imports no analyzer results. If projects exist but no files of the language are indexed, it skips normally. If only TEST files exist, it warns that only test-code results are available.
- Missing protobuf directories or required stream files produce warnings and omit only those output kinds. A malformed protobuf stream is a hard sensor error because the importer cannot establish message boundaries. A message referencing an excluded file is skipped at debug level; a message referencing an unknown non-excluded file produces a warning.
- Missing Roslyn reports cause a warning that files were not analyzed. An unreadable or unrecognized SARIF report is a hard issue-import error for that sensor invocation. Results without messages are skipped. Missing locations degrade as described in section 11.
- Coverage failures are isolated per report and generate analysis warnings; unit-test parser failures are isolated per report, while an aggregate-stage failure produces one language warning. Valid reports and all non-report outputs remain usable.
- Encoding mismatch removes the file before analysis import. Unknown encoding is accepted with a warning. Duplicate case-insensitive paths with conflicting encodings warn because case-sensitive paths are unsupported.
- Highlighting save failure is fatal for that import because overlapping or stale ranges make the whole highlighting object invalid. Symbol and CPD invalid ranges are individually discarded.
- Recovery consists of rebuilding with Scanner for .NET using unchanged sources and reports, correcting report paths or encodings, and rerunning analysis. The plugin has no durable analyzer-owned database state; scanner cache entries are replaceable optimization data.

## 15. Security and trust boundaries

Source, project configuration, SARIF, protobuf, coverage, and test reports are untrusted analysis inputs. The analyzer must inspect syntax and metadata without loading or executing project assemblies as application code. Report paths must resolve only to scanner-indexed files before observations are saved. External diagnostics cannot impersonate unknown Sonar-style IDs because unregistered IDs matching `S` plus three or four digits are rejected rather than created as external rules. Active-rule ID collisions are fatal rather than resolved by precedence.

XML coverage and test reports must be read with the analyzer-commons safe XML factory, which disables unsafe XML features. Wildcard search permits absolute or relative prefixes but rejects `.` and `..` path elements after the first wildcard. Report import may read any path explicitly granted by configuration before checking whether referenced source files belong to the indexed solution; deployment controls therefore own filesystem read permissions and report provenance. Error messages and imported issue text may contain report-controlled content and must be treated as display data, not executable markup.

The family keeps only per-analysis in-memory aggregation and scanner cache output. Concurrent normal rules must not share mutable state without synchronization. Utility report generation is serialized. Regex-based matching uses bounded regex helpers where the analyzer supplies them; operator-configured regular expressions remain a trust boundary and invalid values must fail safely or retain the compiled default.

*Provenance:* `sonar-dotnet-core/src/main/java/org/sonar/plugins/dotnet/tests/XmlParserHelper.java`; `sonar-dotnet-core/src/main/java/org/sonar/plugins/dotnet/tests/WildcardPatternFileProvider.java`; `sonar-dotnet-core/src/main/java/org/sonarsource/dotnet/shared/plugins/SarifParserCallbackImpl.java`; `analyzers/src/SonarAnalyzer.Core/RegularExpressions/WildcardPatternMatcher.cs`.

## 16. Compatibility limits

- Server plugin minimum API is `9.14.0.375`; this release is specified only for Community Build 26.8.0.126808 and Scanner for .NET’s matching report contract.
- Analyzer assemblies require a Roslyn host capable of loading `netstandard2.0` analyzers. Syntax or operation APIs unavailable in the host may disable rules that require them; light-up support must not reinterpret unknown syntax.
- Full server analysis requires Scanner for .NET 5.x or newer. Standalone Scanner CLI is insufficient for C# or VB.NET report production.
- The analyzer-to-plugin protobuf is version-coupled by schema and file name. Unknown fields are protobuf-compatible, but a producer must not change existing field meanings, line bases, or output directory names.
- Highlighting intentionally reduces semantic detail after 4,000 identifiers; symbol indexing stops after 40,000 tokens. These are compatibility limits, not failures.
- Scanner-side path identity is effectively case-insensitive for generated and encoding metadata. Repositories containing distinct files differing only by case are not safely representable by this contract.
- NCover3 remains accepted but deprecated. dotCover HTML has line coverage only. Coverage conditions from different compilers or formats are merged conservatively and may under-report; telemetry records that condition.
- Commercial taint analyzers and private rule repositories are not inferred from public extension hooks and are outside this Community Build specification.

## 17. Acceptance scenarios

1. **C# recognition and metrics.** Given an MSBuild product project with indexed `.cs` files and default settings, when Scanner for .NET supplies matching protobuf and Roslyn reports, the C# sensor imports native issues, all measures in section 8, highlighting, symbols, and CPD under language `cs` and repository `csharpsquid`.
2. **VB.NET separation.** Given a `.vb` product project, when analysis runs, only VB.NET rules and `vbnet` repository issues apply. C# suffixes, Razor behavior, and C#-only keys do not apply.
3. **Generated default.** Given a recognized generated file and default `analyzeGeneratedCode=false`, when analysis runs, the file is filtered and produces no normal rules or measures. Setting the language property to true makes ordinary generated files eligible, subject to indexing and scope.
4. **Razor projection.** Given mapped `.razor` compiler output and `sonar.cs.analyzeRazorCode=true`, when a supported rule reports a mapped diagnostic, the issue appears on the host Razor range. Unmapped generated content produces no host issue. `.cshtml` receives no C# metrics.
5. **Test project scope.** Given a Scanner for .NET project classified as TEST, when analysis runs, test-method declarations and `Tests`-scope rules run, while normal `Main` and ordinary `All` rules do not. The project receives test measures only when report identities match emitted declarations.
6. **Parameterized rule.** Given an active parameterized rule and a valid server-delivered parameter value, when its analyzer instance initializes, the configured value replaces the packaged default. An invalid integer or Boolean leaves the packaged default unchanged.
7. **Third-party Roslyn diagnostic.** Given an unknown rule `CA9999`, a SARIF rule category configured as Bug, and `roslyn.ignoreIssues=false`, when its diagnostic is imported, the result becomes an external issue with engine `roslyn`, configured type, mapped severity, and resilient source location. Setting ignoreIssues true suppresses it.
8. **Reserved Sonar-style ID.** Given an unknown external diagnostic whose ID matches `S` plus three or four digits, when import runs, no ad hoc external rule or issue is created.
9. **Custom native repository.** Given a custom plugin repository beginning `roslyn.` with an active unique rule ID and a matching compiler diagnostic, when import runs, the issue is native under that repository. Activating the same ID in another recognized repository fails configuration rather than selecting one.
10. **Additive coverage.** Given OpenCover and Cobertura paths that match valid reports for one MAIN file, when coverage import runs, line hits aggregate and branch totals use the conservative cross-format merge. TEST, other-language, and excluded files receive no coverage.
11. **Malformed coverage isolation.** Given one malformed report and one valid report, when import runs, the malformed report produces an analysis warning while valid coverage is saved.
12. **Encoding disagreement.** Given a file Roslyn reads as UTF-8 but the scanner indexes with an incompatible charset, when metadata filtering runs, the file is excluded and a warning identifies both encodings.
13. **Ordinary-analysis cache.** Given an enabled scanner cache and a scanner-supplied common base path during ordinary Community analysis, when the cache sensor runs, it stores normalized relative-path hashes for indexed language files and C# `.cshtml` files without changing analysis results.
14. **Large-file degradation.** Given more than 4,000 identifiers, highlighting omits semantic identifier classification but retains lexical classes. Given more than 40,000 tokens, symbol-reference output is absent while other analysis continues.
15. **Catalog completeness.** Loading released JAR `Rules.json` members yields exactly the 456 C# and 197 VB.NET keys enumerated in sections 12 and 13, with exactly the listed parameter keys, types, and defaults; source-only metadata keys listed as not shipped are absent.
